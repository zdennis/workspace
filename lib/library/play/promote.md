You are moving the work in this main checkout into its own workspace with `workspace promote`, then giving the new workspace what you know so its agent can carry on. Promote moves the files and the branch; you carry the knowledge. Do the steps in order.

1. Before you run anything, tell the person what will move. Run `workspace promote BRANCH --dry-run --json` (leave `BRANCH` off to move the branch this checkout is on; on the default branch a name is required) and report `branch` and the paths in `moved.staged`, `moved.unstaged` and `moved.untracked` (a list stops at 200 paths; give the `*_count` too), and every `warnings[]` entry's `message`. Wait for the person to agree before you go on, unless they already told you to move it. Choose the notes to carry: `IMPLEMENTATION_PLAN.md` and `spine/` move on their own; name each other file in the notes directory that belongs to this work by repeating `--carry-note FILE` (a path relative to this checkout's notes directory). Run promote from this pane, and only when no sub-agent of this workspace is still working: promote skips this pane when it looks for working agents and refuses with `agent_working` for any other (its `details.panes` names them; wait for them or ask the person). Do not start a sub-agent before it. Do not use `--force` unless the person says so.
2. Run `workspace promote BRANCH --title "<what the work is, one line>" --spine --plan --carry-note FILE ... --json` (repeat `--carry-note` for each file). Check `ok` and `code` in the answer, not only the exit status. Read `workspace` and `notes_dir` from the answer, and pass `--name <workspace>` to every command below. If it fails, read the error and tell the person. After `move_failed` or `move_incomplete`, run none of the steps below; give the person the commands in `details.recover` if there are any.
3. The goal: `workspace spine goal set --name <workspace> "<one line>"`. This step and the next two need a `spine/`; `notes.spine` in the answer is `moved` or the answer has a `spine` result when there is one. Without it, or when `notes.spine` is `skipped`, tell the person and skip to the plan. If any `spine` command fails (`unknown_item`, `stale_revision`), run `spine show` again and decide from what it says; if it still fails, stop and tell the person.
4. Each stage: decide its status from what was done here. `workspace spine show --name <workspace> --json` lists the stages: `path` is the `<stage-path>` below, and each `Done when` item's `n` is its `--item` number. For a stage whose work is done, first tick each `Done when` item you met and checked, `workspace spine check --name <workspace> <stage-path> --item N --done`, then `workspace spine set --name <workspace> <stage-path> --status completed --note "<where the findings are>"`. A stage partly done is `in_progress` or stays `not_started`, with a `--note` saying what is left. Never mark a stage completed, or tick an item, that you did not verify. Do not pass `--owner`.
5. Stage text: edit the stage files to fit this work, before the new agent starts. Write the prose and the `## Done when` items of each stage, and list the findings files in `artifacts:` (a path relative to the notes directory, or an https URL). The `spine` pack forbids only hand edits of `status:`, `owner:` and the `Done when` boxes; those go through `spine set` and `spine check`. Leave `gates` and `depends_on` alone.
6. The plan: `workspace plan show --name <workspace>` first, then add only the tasks it lacks, in order, each with `workspace plan task add --name <workspace> --title "<task>"`. Add `--state done` for a task finished here (`--state blocked` or `skipped` also needs `--reason "<why>"`). Then add a task "Read HANDOFF.md in the notes directory" and, unless it is now the first task, put it first with `workspace plan task move --name <workspace> --task <its id> --before <first task id>`, so the new agent reads the brief. If `notes.plan` is `skipped`, tell the person. Skip this step when there is no plan.
7. The brief: write `HANDOFF.md` in `notes_dir`. Put in it the goal, what is done and where, the decisions with their reasons, what comes next, and open questions for the person. Refer to files by path. Write it for someone who has seen none of this conversation.
8. Start the new agent, once. When the workspace has a plan: `workspace plan start --name <workspace>`. When it has none: `workspace launch <workspace> --prompt "Read <notes_dir>/HANDOFF.md and continue from it."`. If it is refused or the prompt is not delivered, tell the person what it said; the workspace exists, so never try the other command after one has run, which would start a second agent.
9. Tell the person where the work went: the workspace name, the branch, the path and the brief, and any `warnings[]` from promote that the person has not seen, and any `carried[]` file whose `outcome` was `missing` or `skipped`. Then stop working on this task in the main checkout. Do not keep editing here, do not run the new workspace's work for it, and do not start a sub-agent. The person decides whether to use this session for anything else.

Do not commit the notes. Leave the `IMPLEMENTATION_PLAN.md.moved-*` and `spine.moved-*` files in this checkout's notes directory alone: promote renamed them so nothing was deleted.
