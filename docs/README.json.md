# `--json` output

Every command that takes `--json` prints exactly one JSON value on stdout, and with `--json` nothing is written to stderr for a failure. A failure (refusal, usage error, unknown subcommand) is always the error envelope below. Success is an enveloped object for every command except three, which print their bare document under `--json` and the envelope under `--json-envelope`; see [Success output without the envelope](#success-output-without-the-envelope).

## Success

```json
{"schema_version":1,"ok":true,"workspaces":[],"warnings":[]}
```

`schema_version` and `ok` come first, then the command's own keys (see each command's page).

### Success output without the envelope

With `--json` these commands keep their original success shape, which other tools already parse. Their failures use the envelope with either flag, so check for `ok` being `false` before reading the success shape. `--json-envelope` (it implies `--json`) opts in to the envelope for one call.

| Command | Success shape |
|---|---|
| `list --json` | A bare array: names, or objects with `--show-urls`, `--liveness` or `--all`. |
| `status --json` | A bare object keyed by project name (`{}` when nothing is tracked). |
| `parent --json` | A bare object with `name`, `path`, `git_common_dir`, `is_worktree`, `worktree`; no `schema_version` or `ok`. |

| Command | With `--json-envelope` |
|---|---|
| `list` | `{"schema_version":1,"ok":true,"workspaces":[...],"warnings":[]}`; `workspaces` is the array `--json` prints (also with `--all`, `--show-urls`, `--liveness`). |
| `status` | `{"schema_version":1,"ok":true,"status":{...},"warnings":[]}`; `status` is the object `--json` prints. |
| `parent` | `{"schema_version":1,"ok":true,"parent":{...},"warnings":[]}`; `parent` holds `name`, `path`, `git_common_dir`, `is_worktree`, `worktree`. |

`warnings` is always a list (empty today). The bare `--json` default stays until a later major version. It is a per-call flag, not a config key, so a caller states which shape it parses in the command itself.

To ask which of these a given CLI supports, run `workspace capabilities --json` (see [capabilities](README.capabilities.md)). The shared scope rule for `workflow status` and `plan status`, `--project` included, needs `workflow` 9 and `plan` 6. `workflow status --table` and the `worktree` field need `workflow` 10. The documents themselves are the same as before.

## Actions

These commands take `--json` and print one action document: `add`, `launch`, `stop`, `kill`, `relaunch`, `restore`, `focus`, `repair`, `cleanup`, `deactivate`, `reactivate`, `dev up`, `dev down`, `dev wait`, `dev leave`, `lock release`, `config set`, `config unset`, `config edit`, `daemon restart` (also with `--all`), `agentd restart`, `pipeline start`, `pipeline advance`, `pipeline reset`, `prune`, `ui open`, `binding set`, `binding show`, `binding clear`, `library add`, `library update`, `library remove`, `workflow add`, `workflow update`, `workflow remove`, `workflow run`, `workflow start`, `workflow sweep`, `workflow sweep --install`, `workflow sweep --uninstall`, `workflow sweep --installed`, `workflow resume`, `workflow cancel`, `workflow pause`, `workflow unpause`, `workflow approve`, `workflow reject`, `go` and `step done`. (`finish`, `start`, `lock clear` and `projects stop|kill` have their own pages; `projects stop|kill` use the same shape.) `start --recipe` with a recipe that names a workflow prints this action document, with action `start` and `recipe` (`ref`, `scope`) in the row, in place of the `start` document. `library_recipes` 2 in `capabilities --json` says a CLI does this.

```json
{"schema_version":1,"ok":true,"action":"stop","status":"ok",
 "results":[{"workspace":"api","outcome":"stopped","reason":null,"message":null}],
 "warnings":[],"summary":{"stopped":1}}
```

- `action` is the command's words: `launch`, `dev up`, `lock release`, `config set`, `config edit`, `pipeline start`.
- `results` has one row per target with `workspace` (null when the command has none, such as a global `config set`), `outcome`, `reason` (a short machine-readable cause, or null) and `message`. A row may carry more keys, named on the command's page (`iterm_window_id` for `launch` and `focus`, `play` for `launch --play`, `prompt_sent` and `pane` for `launch` and `pane` for `run --json`, `key`, `value`, `global`, `scope`, `layer`, `file`, `comments_preserved`, `effective` and, only when non-empty, `warnings` for `config set`, the same without `value` for `config unset` (whose `outcome` is `unset`, or `noop` when the key was not set in that file and nothing was written), `effective` keeping the type `config show` uses for the key (a number may be a float, a boolean may be a string), `work_item_ref` for `pipeline`, `run` for `workflow`, and `run_id`, `step`, `attempt` and `reported` for `step done`).
- `outcome` is per command (see its page). `failed` and `refused` count as failures.
- `status` is `ok` (no row failed), `partial` (some did), `failed` (all did, or the command exited non-zero), `cancelled` (a prompt was declined; nothing changed), `dry_run` (`--dry-run` reported the plan; nothing changed), or `refused` (a preflight check refused every target; nothing changed).
- `ok` is `true` for every action document, including `failed`: it means the command ran and reports per-row outcomes. Check `status` and the exit code. A refusal or usage error is the failure envelope above, with `ok: false`.
- `summary` counts rows by `outcome`. `warnings` is a list of strings, each a sentence for a person to read; it is empty when there is nothing to say.
- `rebase --json` is a single result document, not an action document: it exits 0 for every `outcome`, `conflict` and `default_not_updated` included, so a script must read `outcome`. An error (the envelope above) exits 1. When git runs past its time limit during the rebase, the rebase is aborted and the error carries `details.aborted: true` (code `error`); if the abort fails, the code is `rebase_in_progress` with `details.aborted: false`.
- The exit code is 0 for `ok`, `cancelled` and `dry_run`, 3 for `partial`, and 1 for `failed` and `refused`, except that a command that exits with its own code (`dev up` exits 75 after `--max-wait`, `dev wait` after its own) keeps it.
- The progress text a command prints goes to stderr, so stdout holds the one document. A command that reports only an exit code (`dev up`, `dev down`, `dev wait`, `lock release`) gives a `failed` row with `reason: "exit_code"` and `exit_code`; the explanation is on stderr.
- `dev up --json` still runs the project's `pre_dev_up` and `post_dev_up` hooks; their output goes to stderr with the progress text, and stdout keeps the one JSON document (unlike `finish --json`, which skips the `post_kill` hook). See [`dev`](README.dev.md#hooks).
- `focus` puts a sentence in `warnings` for each `focus.chain` step that failed or could not be read, and for a failed `--highlight`; the row is still `focused`. The two errors that can follow the chain, `no_screen_geometry` and `focus_failed`, carry the same sentences in `details.warnings` (absent when there are none). See [`focus`](README.focus.md#focus-chain).
- `kill` adds `"notes_inside_worktree":{"dir":"/abs","files":3}` to its row, and a sentence to `warnings`, when the workspace's notes directory was inside the removed worktree and held files; the key is absent otherwise. `kill` also adds `"dev_stopped": true` to its row when it stopped the worktree's dev environment first; the key is absent otherwise. `kill` always adds `"branch":{"name","deleted","kept_reason"}` to its `killed` row, and `"remote_branch":{"name","remote","deleted","kept_reason"}` with `--delete-remote` (see [`kill`](README.kill.md#branches)). `finish` and `start` have their own pages (`finish` has both keys at the top level; `start` gains `notes_dir` and, when the project's `start.copy_files` applied, `copy_files` with the checkout-relative paths it copied and skipped).
- `config edit --json` opens no editor. Its one row has `outcome: "ready"`, `workspace` (the name whose file it is, null for the global file), `global`, `scope`, `layer`, `file` (the path) and `created` (true when the file was absent and a comment-header stub was written). See [`config`](README.config.md#config-edit).
- `kill` ends the tmux session last. Run it from outside the session it kills, or the process can end before the document prints.
- `stop` with `--json` does not warn about a named workspace that isn't active; it gives that workspace a `not_running` row. When iTerm2 does not answer within 5 seconds, `stop` still stops the workspace and leaves its window open; `warnings` says so.
- `agent run --json` is not an action document. It prints `{"schema_version":1,"ok":true,"workspace":"api","work_item_ref":"wi_12","dispatch_id":"agent-run-ab12cd34","dry_run":false,"reply":{...}}`, where `reply` is the agent's reply as is, including its own `ok`. The exit code is 0 whatever the reply says; read `reply.ok`. With `--dry-run` there is `message` (what would be sent) and no `reply`.

## Workflow status rows

`workflow status --needs-me --json` prints `{"schema_version":1,"ok":true,"generated_at":...,"status":"ok","unreadable":0,"runs":[...],"warnings":[]}`: one row per run waiting for a person, longest wait first; `status` is `partial` and the exit code 3 when `unreadable` run files were left out (`run`, `workflow`, `workspace`, `step`, `attempt`, `code`, `kind`, `gate_file`, `detail`, `since`, `waiting_seconds`, `next_action`, `actions`, and, for a step of a `fan_out` group only (needs `workflow` 60), `group` and `group_state`), `runs` empty and exit 0 when none is and every file was read; `next_action` is for a person, never to run unattended; `--all`, `RUN` and `--table` with it are `usage`. See [what needs you](README.workflow.md#what-needs-you). `workflow status --table --json` prints `{"schema_version":1,"ok":true,"generated_at":...,"rows":[...],"warnings":[]}`: one row per run, with `id`, `workflow`, `state`, `step` (`null` once the run has finished), `workspace`, `workspace_status` (`live`, `stopped`, `gone` or `unknown`), `agent` (`working`, `waiting`, `idle` or `null`), and `has_config`, `has_tmux_session`, `has_worktree`, `has_state_dir` (`true`, `false`, or `null` when it could not be read). The workspace fields describe the workspace now, not when the run ran. See [the status table](README.workflow.md#the-status-table).

A step of a `fan_out` group (needs `workflow` 60) has `group`, `group_state` (`pending`, `running`, `waiting`, `draining`, `failed` or `passed`) and `looping` in its `steps` entry of `workflow status --json`, plus `attempt`, `reason` and `flags` while it is under way; a run with groups adds `groups`, `{GROUP_ID: {"state", "steps"}}`. `workflow sweep --json` yields one row per sibling of a draining group, so rows of a pass can share a `run_id`: tell them apart by `step`, never key on `run_id` alone. Before this release a `fan_out` group stopped for a person could read `draining` instead of `failed`; it now reads `failed`. See [running steps in parallel](README.workflow.md#running-steps-in-parallel-with-fan_out).

In `workflow status --json`, `current.reason` has `code`, `since`, `details` and `actions`. A guard stop that can pass again once the checkout is put back (`head_moved`, `hooks_changed`, `hidden_changed`, `no_commit` with a recorded base) also has `recovery`, a string saying what to put back before `workflow resume`; it is absent otherwise, and for a `no_commit` with no recorded base. Every guard stop also lists `resume --accept-guard` (and `--retry`) actions with `needs: [{"name":"note","flag":"--note"}]`.

Of the action results, only those of `workflow resume` carry `waits` (needs `workflow` 47): null when the resume went through, else an object with `kind` (`parked`, `backoff`, `pane_busy` or `nothing`), `text` (one plain sentence saying what the run waits for) and, by kind, `pane` and `expires_at` (`parked`), `until` (`backoff`) or `pane` (`pane_busy`).

A plain `workflow resume` of a running step whose agent or pane looks gone (needs `workflow` 48) adds `hint` to its action row: one sentence naming `workflow resume RUN --restart-step`. That restart writes the event `step_interrupted` (`step`, `attempt`, `pane`, `usage_counted`) and marks `run_resumed` with `restart_step: true`; a restart made by a reboot recovery also writes `reboot_recovered` (`workspace`, `outcome` `restarted`, `count`); the attempt it closes has the outcome `interrupted` (see [Restarting a crashed step](README.workflow.md#restarting-a-crashed-step)). `next_actions` of `workflow status` and `workflow sweep --json` offer that command for a running step with an open `pane_gone` or `agent_gone` stall.

A running step whose agent exited or whose pane is gone, in a live tmux session, can restart on its own (`workflows.infra_retry.max`, default 2, `0` off; needs `workflow` 50). `workflow status --json` then has `current.infra_retry`, `null` otherwise: `cause` (`agent_gone` or `pane_gone`), `n`, `max` (integer), `due` (ISO string, or null when unreadable), `state` (`scheduled`, `restarting` or `exhausted`) and `reason` (the give-up reason, e.g. `retries_spent`; null unless `state` is `exhausted`). The stall's `current.stuck` and reason stay `stalled`; `--needs-me` and the inbox leave the run out and the `stalled` alert is held while `state` is `scheduled` or `restarting`. `workflow sweep --json` rows for such a stall have action `infra_retry_scheduled` (its `next_actions` is one `workflow status RUN` whose `why` gives the due time) or `infra_retries_exhausted` (resume, resume `--restart-step`, cancel). The history events are `infra_retry_scheduled`, `infra_retry_claimed`, `infra_retry_released`, `infra_retry_ended` and `infra_retries_exhausted` (with `reason`), and `run_resumed` carries `infra_retry` (see [Automatic restarts](README.workflow.md#automatic-restarts)).

A run with a token budget gets a top-level `budget` in `workflow status --json` (needs `workflow` 49 for the keys below). `used` and `spent` leave out the running attempt. `live` is an Integer, or null when the running attempt's tokens are unreadable or no attempt is running (0 means nothing spent yet); `live_spent` is true when `used + live >= allowance` and only means something when `live` is not null; `estimated` counts attempts counted from their `budget_interrupt` record, which an attempt the budget press interrupted carries in `workflow attempts --json` as `{tokens, used, allowance, at}`. A status call reads at most 4 MiB of transcript per run and writes a small derived cache under `<runs dir>/live`.

A running step with no run reason and no park, whose pane's agent turn ended on an API error (needs `workflow` 44), adds `current.turn_failed` to `workflow status --json`, absent otherwise: `since` (ISO string or null), `attempts` (integer, the recovery attempts so far, or null when recovery has no entry for the pane's session), `max_attempts` (integer) and `gave_up` (boolean). Once `workflow sweep` records the stall, the run also has `current.stuck` (`code` `stalled`, `cause` `turn_failed`) for as long as the pane is not `working`; a recovery retry that sets the agent working again hides it.

A continue line the pane refused as busy (needs `workflow` 46) adds `current.refusal` to `workflow status --json` while the run waits to type it again: `error`, `message`, `reason` and `seen` (`state`, `state_since`, `changed_by`, `turn_failed`, `turn_failed_since`, `turn_failed_kind`, `kind`, `last_event_at`, `refusal_reason`, `seen_at`, `read_after`; those present), absent otherwise. A first line refused the same way puts `reason` and `seen` in the `waiting_you` reason's `details`. A review round refused as busy adds `refusal` (the same shape) to `current.review`, absent otherwise. `workflow attempts --json` rows gain `refusal`, null for an attempt never refused. `step_dispatched`, `step_continued` and `review_delivery_failed` events gain `reason` and `seen_*` keys (see [Why a line was refused](README.workflow.md#why-a-line-was-refused)).

A step being reviewed (needs `workflow` 34) adds `current.review` to `workflow status --json`, present only while the step is `reviewing`, stored a round and the run's stored definition still has a `review:` for that step (a finished run has no such key, nor does one whose definition lost its `review:`; a run stored before reviews has no such key). Its keys are always all present: `round` (integer), `max_rounds` (the allowance: the definition's plus `extra_rounds`), `extra_rounds` (integer, what `resume --extra-rounds` added; needs `workflow` 37), `need` (integers), `must` (array), `approvals` (integer, counted from the verdict rows a stopped round read, 0 before that), `pending` (the reviewers with no verdict yet), `pane` and `window` (strings, null until the round is delivered), `delivery` (`delivering`, `failed` or null), `started_at` (null for a held round), `stopped` (boolean: the round ended without deciding), `held` (the reason that kept the round from starting, else null), `next_round` (integer: the round a resume starts, which for a held round, or one `review_no_change` stopped, is that round; null for a round under way), `rerun` (the reviewers a rerun of missing verdicts runs again in the round, else null; needs `workflow` 38), `rounds_spent` (true when `next_round` is past `max_rounds`: the engine starts no such round and refuses the resume with `review_rounds_spent`; needs `workflow` 36) and `reviews` (rows of `reviewer`, `verdict`, `revision`, `counted`, `problem` and `isolation`, each null when the stored row lacks it; `isolation` is `review_pane` for a verdict a sub-agent of the round's own review pane wrote). A step row gains `review_rounds` (the rounds spent) once the step has spent one, and no key before. While a round is under way the review pane is read, not the author's: a permission prompt in it, or an open question asked from it, is `current.reason` `waiting_you` with `details.role` `reviewer` (and `details.kind` `prompt`, `permission` or `ask`) and a `focus` action for the review pane. `current.flags` has `timed_out` when the round has run past the step's `review.timeout` (from the round's `started_at`; a `started_at` that does not parse sets no flag) and `delivering` while its prompt is still being typed. A round that stopped the run has `current.reason.code` `review_incomplete`, `review_rejected`, `review_stale`, `review_guard`, `review_tampered`, `review_rounds_spent` or `review_no_change` (needs `workflow` 38: `details` adds `revision`, `rejected_round` and `rejected_attempt`) (`review_incomplete`, `review_tampered`, `review_rounds_spent` and `review_no_change` are also in the error table below; they are run reasons, not error envelopes), `details` with `step`, `attempt`, `round` and, by code, `problem` and `reviews` (`review_incomplete`), `reviews`, `rounds`, `max_rounds` and `limit` (`run`, `step` or `rounds`; with `attempts` and `max_attempts` for `run` and `step`) (`review_rejected`, needs `workflow` 36: a rejection with rounds and attempts left starts the step again as a new attempt, whose `workflow attempts` row has `retry_of`, and does not stop the run), `rounds` and `max_rounds` (`review_rounds_spent`), `revision` and `revision_now` (`review_stale`), `changed`, `snapshot_head` and `head` (`review_guard`); its `actions` are `workflow resume`, `workflow resume --from STEP` and `workflow cancel`, with `extra_*` needs only when a limit would refuse the start, and no plain `workflow resume` once the step has spent its review rounds (a `review_rejected` with every round spent, a stopped round at the cap, and `review_rounds_spent`). `workflow reject` is not among them: it needs a waiting gate.

`workflow attempts --json` rows (needs `workflow` 34) gain `review` (a summary such as `2/3 approve, skeptic reject`, null for an attempt with no verdict rows), `review_outcome` (`{round, approvals, need, must, passed}`, plus `revision` from `workflow` 38, or null) and `reviews` (the attempt's verdict rows as stored, each with `isolation`, or null); all three are null for an attempt stored before reviews existed. `retry_of` (needs `workflow` 36) is the `attempt` a review round rejected for the attempt that rejection started, null for every other. The text table adds a `REVIEW` column only when some attempt has a summary.

When a step's agent ended its turn with a `WORKFLOW_STATUS:` line, or reported with `step done --status`, the attempt carries `status_report`: `{state, detail, at}` (`state` one of `done`, `running`, `needs_input`, `stuck`; `detail` a string, empty when none) (needs `workflow` 58). The key is present only when the attempt reported one, never `null`. It is on each `workflow attempts --json` row, on `workflow status --json` as `current.status_report` (the current attempt's), and on the `workflow trace --json` transition row that ends the attempt (`status_report`, a symbol-keyed `state`, `detail`, `at`). An explicit report from `step done --status` is stored the same way (its source is not shown) and is consumed by the first judging. A hold for the agent's input (`current.reason.code` `waiting_agent_input`, `details` `step`, `attempt`, `state`, `detail`) also carries it. `workflow insights --json` `holds[].code` reads `waiting_agent_input (needs_input)` or `waiting_agent_input (stuck)` when the hold recorded the state, and plain `waiting_agent_input` otherwise. In the `step done --json` action document the same report reads as `results[].reported` `{status, summary}` — the state and detail under those names; a pass/fail report keeps `status` of `pass` or `fail`, with `code` when one was given.

A gate after a passing review round (needs `workflow` 39) names the round's `summary.md` as its note: the gate's `waiting_you` reason has `details.summary` (the file's path, absent when no summary was written or the run was stored before summaries) beside `artifacts`, and `gate_file` (`name` `summary.md`, `path`, `sha256` now) and `approve --note-sha256` read that file; a summary gone or changed since the engine wrote it is `gate_note_unreadable`. A decided round's `review_outcome` gains `summary` (the path) and the round's entry in the attempt's `rounds` gains `summary` (`{path, sha256}`, or `{problem}`). Each such round upserts one inbox item, dedupe key `review:<run>:<step>`, type `review_request`, `source.kind` `workflow`, `links` `{run_id, step, attempt, round, summary}`, opened again by each later round; none when the step's `review.notify` is false.

`workflow check ID STEP --json` prints `{"schema_version":1,"ok":true,"workflow","step","worktree","passed","command","exit_code","timed_out","error","timeout","duration","log","artifacts","artifacts_created","base_sha","tail","warnings"}` after running the step's `status:` command once, outside any run (no run file, event or lock); `ok` says the check ran and `passed` how it ended, and the exit status is 1 when `passed` is false (needs `workflow` 26; see [trying a check](README.workflow.md#trying-a-steps-check)).

`workflow graph ID --json` (and `--format json`) prints `{"schema_version":1,"ok":true,"graph":{"nodes":[...],"edges":[...],"legend":{}}}` and writes nothing. A node is `{"id","kind","title","annotations"}`: `kind` is `start`, `step`, `gate`, `review`, `fork`, `join` or `end`; `id` is the step id for a step, `<step>.gate` or `<step>.review` for the other two, `<group>.group` and `<group>.join` for the fork and join around a `fan_out` group and `.start` or `.end` for the terminals; a sibling of a group, and its gate node, also has `group` (the group id), and a fork or join has `group_id` (the same id), and the group's `on_fail` goto is a `fail` edge from `<group>.join` (no step id holds a `.`, so none can collide); the `fork` and `join` kinds and the `group`, `group_id` and `loop_key` keys need `workflow` 61, and an older CLI never prints them; the fork's `annotations` are the group's `checkout` and `execution_mode` where set, and the join's are always `{}`; `annotations` holds the step's `produces`, `status`, `require`, `guard`, `uses`, `timeout`, `on_timeout`, `max_attempts` and `context` where set, a review's `from`, `need`, `must` and `max_rounds`, and `origin`, the `extends:` parent a step came from. An edge is `{"from","to","kind","label"}`: `kind` is `next`, `fail`, `reject` or `review_rejected`, and `label` a string or null; a `fail` edge also has `loop_key`, the key of the run's `loops` for it (`STEP->GOTO`, or `GROUP->GOTO` from a join). `legend` holds the run limits that are set (`max_attempts`, `timeout`, `timeout_action`, `stall`, `budget`). With `--run RUN`, each step, gate and review node also has `state` (`passed`, `current`, `waiting`, `failed` or `pending`; a fork or join has no `state`, nor do `.start` and `.end`), each step node `passes` and `attempts`, and each `fail` edge `loops`, the times the run took it (a group's `fail` edge, from its join, reads the run's `GROUP->STEP` loop count). A run of another workflow is `usage`, an unknown RUN `unknown_run`, an unknown ID `unknown_workflow` (see [drawing](README.workflow.md#drawing-a-workflow); needs `workflow` 52).

`workflow render ID STEP --json` prints `{"schema_version":1,"ok":true,"workflow","step","workspace","worktree","inputs","gate","packs","instructions_path","previews":[{"name","value"}],"warnings":[{"code","message"}],"text"}` and writes nothing; `previews` are the placeholder values that belong to a run that does not exist (`run`, `artifacts`, and `workspace` outside any workspace), `warnings` has `not_in_checkout` outside a git checkout, `text` is the composed instructions; a missing required input is `input_required`, an unknown step `unknown_step` (see [rendering](README.workflow.md#rendering-a-steps-instructions); needs `workflow` 25).

`workflow simulate ID --script FILE --json` prints `{"schema_version":1,"ok":true,"workflow","script","inputs","outcome","stopped","capped","max_actions","actions","run":{"state","current","reason","loops"},"steps":[{"id","state","attempts":[{"n","outcome","code"}]}],"budget","transitions":[{"n","at","type",...}]}`; `outcome` is `completed`, `failed`, `cancelled`, `stopped` (waiting for a person) or `capped` (cut off after `max_actions`). It makes no run and writes nothing outside a temporary directory, and answers `invalid_workflow` when writing there fails (a full disk, or `produces: [x, x/y]`); a simulated stop is exit 0. Needs `workflow` 26.

`workflow recover --json` prints the action document with one result for each going run (`run_id`, `workspace`, `step`, `outcome`, `reason`, `message`, `next_actions`; outcomes `restarted`, `restored`, `skipped`, `refused` and `failed`, and `would_restart` and `would_restore` under `--dry-run`). The document also has a top-level `next_actions` with every command a row offers and `unreadable_files`, the paths of run files that could not be read, each also a `failed` row with reason `unreadable_run`. The status is `partial` (exit 3) when some rows are `failed` or `refused`, `failed` (exit 1) when all are, in a dry run too; otherwise it is `dry_run` under `--dry-run` and `ok` if not, both exit 0 (see [Recovering after a reboot](README.workflow.md#recovering-after-a-reboot); needs `workflow` 51).

`workflow sweep --install`, `--uninstall` and `--installed --json` print the action document with one result (`outcome`, `message`, `path`, `label`; `--installed` adds `installed`, `ours`, `loaded` (true, false or null: null means `launchctl` could not answer, exit stays 0, and a script must treat it as unknown, not false), `up_to_date`, `stale`, `interval`, `ruby`, `program`, `scheduled_flag` (true when the entry runs `workflow sweep --scheduled`, false for an entry of ours installed before it, null when none of ours is installed; needs `workflow` 49). `workflow sweep --json` prints the action document with one result for each run looked at (`outcome`, `reason`, `message`, `run_id`, `step`, `attempt`, `cause`, `action`; see [sweeping stopped runs](README.workflow.md#sweeping-stopped-runs); needs `workflow` 15; outcome `redelivered`, with `cause` `undelivered` and `action` `redeliver`, is a step's undelivered line typed again, needs `workflow` 17, and the failed attempt then carries `redelivered: true` in the run file and does not count against `max_attempts`; outcome `retried`, with `cause` `retry_backoff` and `action` `retry`, is an `on_fail` retry started after its `backoff`, and a run still waiting is `nothing` with `reason` `backoff` and the same `cause`; needs `workflow` 18): status `dry_run` under `--dry-run`, otherwise `ok` unless a result is `failed` (a daemon that could not be started, an interrupt that failed, a missing program, an unreadable run file): `partial`, exit 3, or `failed`, exit 1, when all did; `summary` counts the results by outcome, and `next_actions` lists what a person can run about the rows it left alone (see [next actions](#next-actions); needs `workflow` 42). A failed step the sweep timed out has `details.code` `step_timed_out`. A failed step waiting out an `on_fail` `backoff` reads `state` `waiting` with the reason `retry_backoff` (`details`: `step`, `attempt`, `to`, `until`, `seconds`, `loops`; actions `workflow resume`, which starts the retry now, and `workflow cancel`); the run file holds `backoff` (`until`, `to`, `context`, `text`) until it starts, and no `backoff` key in a run stored before this (needs `workflow` 18). Attempts are not listed in `workflow status --json`; `workflow attempts RUN --json` prints them (see [reading a run's attempts](README.workflow.md#reading-a-runs-attempts); needs `workflow` 12). `workflow stats ID --json` prints the per-step figures of a workflow's runs (`{"schema_version":1,"ok":true,"workflow":ID,"status":"ok"|"partial","last","since","workspace","project","definition","runs","unreadable","undated","unattributed_resumes","steps":[{"step","attempts","passed","failed","not_delivered","unfinished","median_seconds","resumes","tokens_from_unfinished","tokens":{"mean","runs_counted","runs_uncounted"}}]}`; `status` `partial` with exit 3 when a run file could not be read; a null `tokens.mean` means no run recorded tokens, never zero; see [step statistics](README.workflow.md#step-statistics); needs `workflow` 23). `workflow compare ID --json` prints the runs in groups (`{"schema_version":1,"ok":true,"workflow":ID,"status":"ok"|"partial","last","since","workspace","project","by","runs","matched","without_pack","no_attempts","unreadable","undated","warning","groups":[{"key","sha","runs","settled","first_try","pass_first_percent","running","cancelled","resumes","resumes_per_run","run_ids"}]}` (`run_ids` lists the group's run ids, newest first); `warning` is always present, `partial` with exit 3 as for stats; a bad `--by` is a usage error; see [comparing runs](README.workflow.md#comparing-runs); needs `workflow` 24). `workflow audit RUN --json` prints `{"schema_version":1,"ok":true,"run":ID,"step":STEP-or-null,"clean":bool,"counts":{},"directory":...,"files":[...],"without_evidence":[...],"event_errors":{"count":n,"entries":[{"ts","run_id","type","errno","message"}]},"next_actions":[...]}` and exits 1 (the document still printed, `ok` true) when `clean` is false: a kept copy changed, is missing or was replaced (see [auditing a run's evidence](README.workflow.md#auditing-a-runs-evidence); needs `workflow` 14; `next_actions` needs `workflow` 42; `event_errors` lists every one of the run's history lines that could not be written and never changes `clean` or the exit status; needs `workflow` 45). The run file keeps each attempt's `head`, `definition_sha256`, `prompt_sha256`, `packs`, `outputs`, `check.command`, `session`, `agent`, `usage` (a main-thread count, null rather than an undercount), `evidence` (the copies of the prompt, check log, outputs and, kind `review`, each review round's verdict files kept in the state directory, with their hashes; needs `workflow` 13, the `review` copies `workflow` 33) and `reasons` (the run file's own `reasons` list holds the waits outside any attempt, each with a `step`; join them to attempts by `step` and time) (see [what an attempt records](README.workflow.md#what-an-attempt-records)).

`workflow insights ID --json` (needs `workflow` 56) prints `{"schema_version":1,"ok":true,"workflow":ID,"status":"ok"|"partial","runs","last","since","workspace","project","stored","unreadable","undated","enough","hot_steps","themes","observations","failures","holds","effects","next_actions"}`: counts, step ids, reviewer names, codes and run ids, never a reviewer's or an agent's text. `status` `partial` with exit 3 when a run file could not be read; `enough` is false below 3 runs. `hot_steps` lists every step `stats` returns (empty `retry_run_ids` and `resume_run_ids` allowed); only the text output keeps the retried or resumed ones. Row shapes are in [Insights](README.workflow.md#insights).

`workflow learn reflect RUN --json` (needs `workflow` 57) prints `{"schema_version":1,"ok":true,"run":ID,"pane":PANE,"path":PATH,"instructions":PATH,"exists":false}` when it started a reflection pane, and `{"schema_version":1,"ok":true,"run":ID,"path":PATH,"exists":true,"text":TEXT,"truncated":bool}` when `reflection.md` already exists and nothing was started; `text` is cut at 200,000 bytes and `truncated` says so. Error codes are in the table below. See [Reflecting on a finished run](README.workflow.md#reflecting-on-a-finished-run).

A run whose definition declares `timeout:` has a top-level `deadline` in `workflow status --json` (`timeout`, `action`, `extra_seconds`, `limit` and `used`, all in seconds, and `spent`; `needed` and `suggested` are not in the row but in the actions' `extra_time` need), and an action that would start an attempt while it is spent lists the need `{"name":"extra_time","flag":"--extra-time","min":N,"suggested":M}` (`min` and `suggested` in seconds; pass a duration such as `15m`); the inbox row kind for a held run is `workflow_run_timed_out`. Needs `workflow` 33.

Each step row of `workflow status --json` has `gate_note`, the text given to `approve` or `reject` with `--note` (or `null`), beside `gate_file` and `note_changed`. `worktree`, the checkout path stored with the run (or `null`), is on every row of `workflow status --json` and on the `run` object of every `workflow` action document. Both need `workflow` 10.

A failed step whose `on_fail` retry waits out a `backoff` has the run file's `backoff` (`until`, `to`, `context`, `text`, and `pane` and `identity`, the pane the run was in and its session and slot) and the reason `retry_backoff`. When the retry came due and that pane was no longer the run's, `backoff.blocked` is `pane_has_run`, `pane_gone` or `pane_changed`, nothing was typed, and the run reads `waiting` with the reason `waiting_you` (`details.kind` `dispatch`, `details.error` the same code; `pane_gone` for a gone pane), whose `actions` are `workflow resume` (needs `--pane`) and `workflow cancel`. `workflow resume --pane PANE` with another agent pane starts the retry. `workflow sweep` reports such a run as `nothing` with `reason` `retry_blocked`, which is not a failure. `workflow resume` (without `--pane`) of a held wait starts nothing and writes no rebind, note or `run_resumed` event; repeating it changes nothing, except that a hold whose cause or pane changed since is recorded once (a new reason and one `step_retry_blocked` event) and returns the result outcome `unchanged` (`message` "Nothing was done: ..."), which is not a failure: exit status 0, with `--json` too. `reason` and `message` of that result, and `workflow status --json` (the run's `reason` with `details.error`, and the run file's `backoff.blocked`), tell a script why. The outcome `unchanged` is also what `workflow resume` answers when an agent is still working on the step or a check is running.

`workflow show ID --json` and `workflow validate --json` add `workflow.extends` when the definition has `extends:`: the parents nearest first, each `{"id","source","path","sha256"}` (the parent file's text digest); the key is absent otherwise. `workflow.sha256` stays the file's own; `workflow.resolved_sha256` (always present) is the digest a run started now would store as `definition_sha256`, which covers the parents too. A parent that can't be used is reported alone, each problem prefixed `extends ID (PATH):`. `workflow add`, `update` and `remove` rows gain `extended_by` (ids of the definitions that extend the one changed, with `ID (project NAME)` for a project's) only when there are some, with a stderr warning. A bad `extends:`/`replace:` is `invalid_workflow` with every problem in `details.problems`. They also add `workflow.imports` when a step has `import:`: one entry per imported step, `{"step","import","layer","path","overrides","removes","shadows","sha256"}` (`import` as written; `layer` where a bare name was found, null for `PATH#NAME`; `path` the library file; `overrides` the keys the step sets; `removes` the library keys gone from the result, a `prompt_file` a `prompt` replaced included; `shadows` the lower-layer files of that name; `sha256` the library step's digest); the key is absent otherwise. An override that drops library values is a warning of code `import_dropped`. `workflow validate PATH --json` on a file in a layer's `steps/` directory checks it as a step library and prints `{"library":{"path","scope","valid","steps","problems"},"importers":[{"id","source","project","path","valid","problems"}]}`, one importer per workflow in any layer or project whose import reaches the file; when the library or any importer fails it is `invalid_step_library` with the same two keys in `details`.

`workflow validate --json` adds a top-level `warnings` array beside `workflow` (empty when there are none); `workflow.scope` is `project`, `global` or `builtin` when the PATH sits in that definitions directory, else `null` (`workflow.source` stays `file` or `stdin`). Each entry is `{"code":CODE,"step":STEP_ID,"message":TEXT}`. `step_without_proof`: a step with no `produces`, `status`, `require` or `gate` passes on any turn end. `timeout_action_without_timeout`: the workflow sets `timeout_action` with no `timeout` (`step` is `null`). `on_timeout_without_timeout`: a step sets `on_timeout: interrupt` or `fail` with no `timeout`. `on_fail_exceeds_max_attempts`: the retries of a step's `on_fail.max` can't all start under `max_attempts`. `on_fail_exceeds_step_attempts`: the step an `on_fail` goes back to has a `max_attempts` below `on_fail.max + 1`. `step_attempts_exceed_run`: a step's `max_attempts` is above the workflow's. `review_dropped`: a `replace:` step leaves out the `review:` of the parent step it replaces. `review_rounds_reach_step_attempts`: a step's `review.max_rounds` is at or above its own `max_attempts`. `review_rounds_exceed_run_attempts`: `review.max_rounds` is above what the workflow's `max_attempts` leaves for the step. `unknown_pack`: an `include:` (a reviewer's too) names a pack the library can't find from the current project (`step` is `null` for the workflow's own). `command_unset`: a step needs `commands.test` or `commands.lint` and the project has none. `agent_not_claude`: the project's main agent is not Claude Code (nor `none`), so the step's `WORKFLOW_STATUS:` line is not read, `budget:` never stops the run, and restore, recover and infra retry do not resume it (`step` is `null`). A top-level `not_checked` array (same entry shape; codes `pack_not_checked`, `commands_not_checked`, `agent_not_checked`) lists what these checks could not check: outside a git checkout, or (`commands_not_checked` only) when the project's config file does not parse. Warning codes are an open set: callers ignore codes they do not know. Only `workflow validate` reports warnings; `show`, `start` and `run` do not. A warning is not an error code: `ok` stays `true` and the exit code 0. See [Validating a definition](README.workflow.md#validating-a-definition). `fan_out_edits_unverified`: a `fan_out` group sets `checkout: shared-edit` (`step` is the group's id), so the engine can't verify that its siblings edit disjoint paths.

## Next actions

A next action is a command a person could run, as data: `{"action","args","needs"}`, plus `"why"` when the command can say why it is offered (the key is left out otherwise). `workspace ACTION ARGS...` runs as it stands when `needs` is empty. Each entry of `needs` is a value the person supplies: `{"name","flag"}` (`flag` is null for a positional value), with `min` and `suggested` for a spent limit. `needs` lists inputs, not who should run the command.

```json
{"action":"workflow resume","args":["wr_2611151200ab12"],"needs":[{"name":"extra_tokens","flag":"--extra-tokens","min":40000,"suggested":80000}],"why":"budget_spent"}
```

One builder makes every one, and the same shape is read in several places:

| Where | Key |
|-------|-----|
| `workflow audit --json`, `workflow sweep --json`, `plan status --json` | `next_actions`, an array (empty when nothing needs a person) |
| `workflow status --json`, `current.reason` and `current.stuck` | `actions`, an array |
| `workflow status --needs-me --json` rows | `next_action` (the first of `actions`) and `actions` |
| `inbox list --include-derived --json` workflow rows | `links.next_action` |
| `goal show --json` | `next.action` |

`actions`, `next_action` and `links.next_action` are older names for the same shape. They keep their names and values for compatibility, and a reader can treat all of them alike.

A next action is a suggestion for a person, or for a caller acting for one. Nothing in workspace runs one unattended, and a script or agent should run only the ones its task allows: `approve`, `reject`, `resume --accept-guard` and `cancel` wait for the person to ask.

## Snapshot

The agent daemon's pane list (`sessions --json`) carries a boolean `turn_failed` per pane, `true` while the agent's last turn stands as ended by an API error (see [`sessions`](README.sessions.md), and [`agentd`](README.agentd.md#recovering-from-an-api-error) for the recovery). The panes of `snapshot --json` don't list it. Each `sessions --json` pane also carries `state_changed_by` (the input its `state` comes from, or null) and, while `turn_failed` is true, `turn_failed_kind` (see [`sessions`](README.sessions.md)).

`workflow events RUN --follow --json` prints `{"type":"follow_started","run","since","state","current","definition_sha256"}`, one event per line, a `{"type":"gap","at","run","reason":"history_shorter"|"not_retained","next_since"}` line when lines were lost, and a last `{"type":"follow_ended","run","state","reason":"completed"|"cancelled"|"killed"|"failed"|"pruned"|"timeout","next_since":N}`. The exit code is 0, 1 (the run ended cancelled, killed or failed) or 75 (`--timeout` ran out); see [`workflow events`](README.workflow.md#following-a-runs-events). `daemon watch --json` prints one object per line: `source` (`daemon`, `run` or `watch`), `at`, `type`, `workspace`, `run_id`, `event` and an opaque `cursor` to pass back as `--since`; a `--run` watch ends with a `follow_ended` line carrying `state` (see [`daemon watch`](README.daemon.md#watch)).

`workflow trace RUN --json` (needs `workflow` 54; `workflow_trace` 1) prints `{"schema_version":1,"ok":true,"run","trace_id","transitions","spans","totals","warnings"}`; with both `--json` and `--table`, `--json` wins. A value the run never recorded is `null`, never 0. The keys of each part are in [Tracing a run](README.workflow.md#tracing-a-run).

The same pane list carries `waits` per pane: every open wait as `agent_id`, `tool`, `input` and `since` (the main agent's `agent_id` is `null`). `input` is as sensitive as `waiting_input`, and the panes of `snapshot --json` leave `waits` out (see [`sessions`](README.sessions.md)).

`snapshot --json` prints one read-only document of everything a UI polls (see [`snapshot`](README.snapshot.md)). `--json` is required; a source that can't answer is reported as unavailable (null fields, `daemons_unavailable` rows, `warnings`) rather than as clean, and the command still succeeds. Its `cursor` is `ev:<inode>:<byte offset>` of the event log.

`ui status --json` prints one read-only document: `{"schema_version":1,"ok":true,"running","pids","handler","links","probe","warnings"}`. It opens nothing. A probe that cannot answer is `ok: true`, exit 0, with `running`, `pids` and `handler` null and `probe` naming the problem; a usage error is the error envelope (see [`ui`](README.ui.md#status)).

## Goal

`goal show [REF] --json` prints `{"schema_version":1,"ok":true,"goal":{...},"warnings":[]}` and `goal list [--all] --json` prints `{"schema_version":1,"ok":true,"goals":[...],"warnings":[]}`. Both are read-only; a source that can't answer is a null level plus a warning. `show` also carries `done_means` and `not_yet` (lists of `{code, text}`) and `delivery`, and `list` rows `delivered` and `not_yet_codes`: a finished plan or spine is `done` only once the branch's commits are on the default branch (local git only). Every field, the closed value sets, nullability and warning codes are in [README.goal.md](README.goal.md).

## Work queue

`work-queue` (alias `wq`) action verbs (`add`, `rm`, `move`, `cancel`, `enable`, `disable`, `resume`, `skip`, `advance`, `history clear`) print an [action document](#actions) with two more top-level keys, `queue` (the workspace) and `revision` (the queue file's revision, which `move --if-revision` takes). Each row is `{"workspace","outcome","id","position","kind"}`; `id`, `position` and `kind` are null where no item applies (`enable`, `resume`, `history clear`, an `advance` refusal). There is no `message` key. Rows add keys where they apply:

- `advance` rows (and the pass rows of `cancel --and-continue`) add `reason`, `run_id` and `next_actions`; `id` and `kind` are null on a refusal.
- An `add` or `enable` row adds `warnings` (`daemon_not_started`, with `workspace` and `message`) when the agent daemon could not be started; the change itself is made. A `cancel` row adds `run_id`, and `skip` adds `run_id` and, while the run still goes, `warnings` (a list of `{code, message}`; the document's `warnings` carries them too) and `next_actions`.
- `history clear` adds `count`.

`outcome` by verb: `add` gives `added` or `unchanged`; `rm` `removed`; `move` `moved` or `unchanged`; `enable` `enabled` or `unchanged`; `disable` `disabled` or `unchanged`; `resume` `resumed` or `unchanged`; `skip` `skipped`; `cancel` `cancelled`; `history clear` `cleared`, `unchanged` or `cancelled` (the question was answered no). For `advance`:

| Outcome | `reason` |
|---------|----------|
| `started` | none; `run_id` is the new run |
| `succeeded` | none; the item's run completed |
| `active` | none; the run goes on |
| `held` | `gate`, `parked`, `failed_check`, `budget_spent` or `run_timed_out` |
| `failed`, `cancelled` | the run's state; the queue paused unless the item had `--on-fail continue` |
| `unchanged` | `disabled`, `paused`, `empty`, `run_going` or `starting` |
| `launch_failed` | `unknown_kind`, `usage_error`, `start_failed`, or the error code of the failed start |
| `interrupted` | `interrupted` (a start whose process died, with no run found) or `unknown_run` (the item's run is gone) |
| `claim_lost` | `claim_lost` |

The status and exit code of `advance` and of `cancel --and-continue`: `failed` (1) when every row ended badly, `partial` (3) when some did, else `ok` (0). Ending badly is `launch_failed`, `claim_lost` or `interrupted`, and a `failed` or `cancelled` run only when the queue paused for it (a row that offers `work-queue resume`), not under `--on-fail continue`. A held item and the `cancelled` row of `cancel --and-continue` are not counted, so a pass that fails after the cancel gives `partial`.

```json
{"schema_version":1,"ok":true,"action":"work-queue add","status":"ok","queue":"api.worktree-x","revision":4,
 "results":[{"workspace":"api.worktree-x","outcome":"added","id":"3fa9c1d2","position":2,"kind":"workflow"}],
 "warnings":[],"summary":{"added":1}}
```

The reading verbs print a success document with a `warnings` list and their payload beside it:

| Verb | Keys |
|------|------|
| `list`, `status` | `queues`: one per workspace, each with `workspace`, `state` (`on`, `off` or `paused`), `paused_reason`, `daemon_running` (whether its agent daemon answers; `false` on an off queue is no fault), `revision` and `next_actions` (`agentd --ensure` and `work-queue advance` only for an enabled queue whose daemon is down); `warnings` has a `daemon_not_running` `{code, workspace, message}` for each such queue; `list` adds `enabled` and `items` (item rows), `status` adds `active` (an item row or null) and `queued` (a count) |
| `show` | `workspace`, `item` (the full item: its `spec`, `result` and the rest, plus `position`, `what` and `run_id`) and `next_actions` |
| `active` | `workspace`, `item` (an item row, or null when nothing is active), `waiting_on` (`on`, `reason`, `run_id`, `run_state`, `step`; null with no item) and `next_actions` |
| `history list` | `entries`, each a finished item with `outcome`, `reason`, `finished_at` and `workspace`, and `next_actions` |
| `history show` | `workspace`, `entry` and `next_actions` (the `work-queue add` that queues it again) |

`list --watch` and `active --watch` are refused with `--json` (a usage error), because a redrawn screen is not a document.

An item row, as `list`, `status` and `active` give it, is `{id, position, state, kind, what, headless, on_fail, added_at, started_at, reason, run_id, dedupe_key}`; `state` is `queued`, `starting`, `active` or `held`. `show` gives the whole item, with `spec`, `added_by` and `result` (`run_id`, `log_path`, `error`). See [`work-queue`](README.work-queue.md).

## Tmuxinator templates

`template list [--scope SCOPE] [--name WS] --json` prints `{"schema_version":1,"ok":true,"workspace":...,"selected":{"project":{...},"worktree":{...}},"templates":[...],"warnings":[]}`. Each `templates` row has `name`, `ref`, `scope`, `project`, `description`, `path`, `files`, `effective` and `selected_for` (the kinds, `project` and `worktree`, that render from it for that workspace). `selected.<kind>` is `{name, scope, source}`, or null with a warning (`code`, `kind`, `message`) when the set it names can't be found; an edited copy `init` installed shows as the set `legacy`. `template show [NAME] --json` prints `{"schema_version":1,"ok":true,"templates":[...],"warnings":[]}` with one row per file (`kind`, `template`, `scope`, `source`, `path`, `content`, `sha256`), and `template path --json` the same rows without `content` and `sha256`. `source` is where the set's name came from (`worktree`, `project`, `global`, `default`, `legacy`), or `argument` when NAME was given. All three read only. `template variables [--kind K] [--name WS] --json` prints `{"schema_version":1,"ok":true,"variables":[...],"warnings":[],"workspace":...}`; each row has `name`, `kinds`, `required` (per kind), `description`, `source`, `sample`, `whole_line` and, with `--name`, `value` (null when the record holds none), and `value_state` (`recorded`, `no_record`, or null without `--name`) is set at the top; `value` is what `render --name` would fill (the agent command from current settings, `PRE_WINDOW` as its line or `(dropped)`). `template render ... --json` prints `{"schema_version":1,"ok":...,"template":...,"source":...,"path":...,"kind":...,"workspace":...,"inputs":{...},"content":...,"diff":...,"warnings":[...]}`: `template` is the set's name (null for `--file`), `content` the filled text (null when the renderer refused), `diff` the unified diff under `--diff` (with `changed`, true or false, only then), and `warnings` the file's problems (`severity`, `code`, `kind`, `message`); `ok` is false, and the exit status 1, when one is an error. Neither writes anything; a workspace with no render record is `no_render_record` for `render --name`.

`template validate [NAME | --file F] --json` prints `{"schema_version":1,"ok":...,"files":[{"kind","template","path","problems":[{"severity","code","kind","message"}]}],"errors":N,"warnings":N}` (`template` is null for `--file`). It is not an error envelope: a problem is reported in the document, with `ok` false and exit 1 when any is an error, and `ok` true and exit 0 for warnings alone. `template diff [NAME] [--against NAME] --json` prints `{"schema_version":1,"ok":true,"files":[{"kind","template","path","against_path","changed","diff"}],"warnings":[],"against":NAME,"changed":bool}`; it always exits 0, `warnings` is always empty, and `diff` is the unified text, empty when the files are the same.

`template new NAME`, `template edit [NAME]` and `template use NAME` change something, so under `--json` each prints the action document (`{"schema_version":1,"action":"template new"|"template edit"|"template use","status":...,"results":[row],...}`) and exits through its `status`. The `new` row has `outcome: "created"`, `template`, `scope` (`global` or `project`), `path`, `from` (the set copied) and `warnings` (the copy's problems, as in `validate`, and a `shadows_template` entry with the hidden set's `scope` for each lower-scope set of the same name the copy now hides); a name already in that scope is `template_exists`, an invalid source `invalid_template`. The `edit` row has `outcome` `edited`, or `failed` with `reason: "invalid_template"` (exit 1) when a file has an error, `template` and `files` (`kind`, `template`, `path`, `problems`); `--json` opens no editor and checks the files as they are, and a built-in set is `template_builtin_readonly`. `template export DIR` and `template import PATH` print the same action document. The `export` row has `outcome` `exported` (or `nothing_to_export`), `scope`, `dir`, `templates` (each `template`, `path` and `files`, relative path to sha256) and `warnings` (`legacy_not_exported` when the `legacy` set was skipped); a set's folder already in DIR is `template_exists`, a DIR in the library a `UsageError`. `templates.json` in DIR is written for people to read (`schema`, `workspace_version` and every set folder in DIR with its files' sha256) and `import` does not check it; dotfiles are left out both ways. The `import` row has `outcome` `imported` or `unchanged`, `scope`, `backup` (the id of the backup batch holding what was replaced and the sets added, else null) and `templates` (each `template`, `outcome` `added`, `replaced` or `unchanged`, `scope`, `path`, `warnings`); an invalid set, or one holding a symbolic link (problem code `symlink`), is `invalid_template` and nothing is written, a replaced set a key selects, or a new `default` that would hide the built-in one, is `template_in_use`; a set that hides a lower scope's has a `shadows_template` entry in its `warnings`. The backup batch is put back with `template restore ID`, whose rows for its template sets have `template` and `scope` in place of a workspace. The `use` row has `outcome: "selected"`, `template`, `key` (`tmuxinator.template`, or `tmuxinator.worktree_template` with `--kind worktree`), `layer` and `file`; a name no set has is `unknown_template`.

`template status [WS...] [--all | --project [NAME]] --json` prints a read document: `{"schema_version":1,"ok":true,"workspaces":[...],"warnings":[],"counts":{"current":N,"stale":N,"modified":N,"untracked":N}}`. Each `workspaces` row has `workspace`, `state` (`current`, `stale`, `modified` or `untracked`), `kind` (`project` or `worktree`, from the render record; null with no record), `template` (the set the record says the config was rendered from, null with no record), `selected` (the set a render would use now, null when it can't be resolved or the config is untracked), `stale` (true when a render today would differ from the last one or name another set), `reasons` (why: `template_switched`, `template_changed`, `agent_changed`, `template_unavailable`, `render_failed`; empty for `current` and `untracked`) and `approx` (true when the record was adopted by `template adopt` without an exact render, so `modified` may not mean a hand edit). It reads only and always exits 0, whatever the states; a script that must act reads `state` or `counts`.

`template apply [WS...] [--all | --project [NAME]] --json` prints the action document (`"action":"template apply"`) with one row per workspace (`workspace`, `outcome`, `reason`, `message`, `state` (where it stood, as in `template status`), `template` (the set it renders from now), `running` (true when its tmux session is up and its config was rewritten, so a relaunch takes the new layout), `record_only` (true when another set renders the same text, so only the render record was rewritten and the config's bytes were left alone), `code`, and `diff` under `--diff`: the unified diff, null when nothing would change) and three more top-level keys: `backup`, the id of the batch every written config and render record was copied into first (null under `--dry-run` or when nothing was written), `rolled_back`, and `skipped`, the skipped rows counted by `reason` (`{}` when none). `outcome` is `applied` (`would_apply` under `--dry-run`), `unchanged`, `skipped` (`reason` `modified` with `code` `template_modified`, `approx` with `code` `template_approx` (a record `template adopt` made without an exact render), `untracked`, `gone` for a config renamed or removed while apply waited for the workspace's lock, `not_reached` after a roll back), `failed` (`reason` and `code` the error code: `workspace_locked`, `backup_symlink`, `error`, ...) or, under `--rollback-all-on-error`, `rolled_back` for a row put back. Status `ok`; `dry_run` under `--dry-run` (nothing written, no batch, no lock taken); `partial` (exit 3) when some rows failed and `failed` (exit 1) when all did or the batch was rolled back. Skipped rows are not failures: a run that skips every hand-edited or untracked config is `ok` with exit 0, so a script that must know reads `skipped` (or each row's `reason`). `warnings` entries are `{code, message, ...}`: `rollback_left_file` (`workspace`, `kind` `config` or `record`, `path`: a file that changed after apply wrote it was left, and that row stays `applied`; for `kind` `record` alone the config was put back), `rollback_failed` (`workspace`: its files could not be put back, the row stays `applied`), `rollback_unreadable` (nothing was put back) and `prune_failed` (old batches stayed). `remove`, `kill` (and `finish`) and `prune` delete a config inside the same startup lock, so apply never writes a removed config back.

`template restore BACKUP_ID [WS|TEMPLATE...] [--force] --json` prints the action document (`"action":"template restore"`) with one row per workspace and template set of the batch (`workspace`, null for a set, which carries `template` and `scope`; `outcome` `restored`, `unchanged`, `skipped` (`reason` `gone`) or `failed` (`reason` and `code`: `restore_conflict`, `workspace_locked`, `backup_incomplete`, `error`, ...); `reason`, `message`, `code`; `files` on a restored or conflicting workspace row; and on a `restored` workspace row `config_rewritten`, true when the tmuxinator config's bytes changed, false when only its render record did or the restore deleted a config the batch had created) and the top-level keys `backup` (the batch the restore took first), `restored_from` and `skipped`. Exit 3 when some rows failed, 1 when all did.

`relaunch [WS...] [--all] --json`, when the workspaces include the one whose tmux session the command runs in (the session that holds `$TMUX_PANE` or is the `$TMUX` client's; the working directory alone does not count, since a stop can't hang up a terminal outside the session), stops nothing itself: it starts `workspace relaunch -- NAMES...` in a background run outside its tmux session and returns at once, status `ok`, exit 0, one row per workspace with `outcome` `relaunch_scheduled`, and two more top-level keys: `log`, the background run's log (`<state>/.relaunch/<time>-<pid>.log`, where the run's output and its exit go; the newest 20 are kept), and `pid`, the background run's pid. `relaunch_scheduled` means only that the background run started. Its result is the log's last line, `[time] exited N` (N the background relaunch's exit status, as without `--json`); that line is absent when the run was killed. A run that could not be started is the error `relaunch_detach_failed`, and a workspace another background run is still relaunching `relaunch_in_progress`. Otherwise the rows are `relaunched`, or `failed` as for `launch`.

`template apply ... --relaunch --json` and `template restore ID ... --relaunch --json` print the same document with one more field on each row a relaunch could concern (an `applied` row that is not `record_only`, `would_apply` under `--dry-run`, or a `restored` workspace row whose `config_rewritten` is true): `relaunch`, which is `relaunched` (its session was stopped and launched again from the new config), `failed` (with `relaunch_code`: `relaunch_stop_failed` when its session was still up after the stop, so it was not launched; else `relaunch_launch_failed`, the launcher's own reason kept in the warning's message), `would_relaunch` under `--dry-run` (nothing is stopped; the status stays `dry_run`), `skipped` (with `relaunch_code` `relaunch_own_workspace` for the workspace the command runs in, which is never relaunched, dry run included: the workspace of the working directory, and also, when `$TMUX_PANE` is set, any whose tmux session (asked on that workspace's own tmux socket, session names compared as tmux stores them, `.` and `:` as `_`) holds that pane, or, with `$TMUX` set where `$TMUX_PANE` is unset or tmux can't place it for that workspace, whose session is the one whose id `$TMUX` names (its third field); or `relaunch_skipped` after a roll back), `not_active` (its session is up but the state file does not track it) or `not_running` (its session is not up). `relaunch_code` is one of those four codes, and is absent otherwise. Without `--relaunch` the rows have no `relaunch` field (restore rows always carry `config_rewritten`). With the flag one more top-level key lists the names, even when empty: `relaunched`, the workspaces relaunched; a dry run emits a key named `would_relaunch` in its place, the workspaces it would relaunch. A relaunch that fails makes an `ok` status `partial` (exit 3); a `partial` or `failed` status the rows already gave stays; `skipped`, `not_active` and `not_running` change no status. Warnings: `relaunch_failed` (`workspace`) for each failure, `relaunch_own_workspace` (`workspace`, naming `workspace relaunch NAME` to run from outside it), `relaunch_not_active` (`workspace`, to stop and launch it by hand), `relaunch_own_workspace_unknown` (`pane`, null when only `$TMUX` is set: neither `$TMUX_PANE` nor the `$TMUX` session answered for any workspace asked about, so the working directory alone decided), the stop command's own as `relaunch_stop_warning`, and after `--rollback-all-on-error` rolled the batch back nothing is relaunched and one warning is `relaunch_skipped`. The progress text of the stops and launches goes to stderr.

`template backup [WS...] [--all | --project [NAME]] --json` prints the action document (`"action":"template backup"`) with one row per workspace (`workspace`, `outcome` `backed_up`, `skipped` (`reason` `gone`) or `failed` (`reason` and `code`: `backup_symlink`, `workspace_locked`, `error`), `reason`, `message`, `code`) and the top-level `backup` (the `manual` batch's id, null when nothing was copied) and `skipped`. `template backups list --json` prints a read document, not an action (it has no `action`): `{"schema_version":1,"ok":true,"backups":[{"id","created_at","reason","workspaces":[...]}],"warnings":[]}`, newest first, and reads only. `template backups prune --json` prints the action document (`"action":"template backups prune"`) with one `pruned` row (`id`) per batch removed and `kept`, the batches left. `template restore ID [WS...] [--force] --json` prints the action document (`"action":"template restore"`) with one row per workspace of the batch (or the ones named): `outcome` `restored` (`files`: `config`, `record`), `unchanged` (both files already as the batch has them), `skipped` (`reason` `gone`: the config and record are gone and the checkout the batch's record names is gone too; a config deleted by accident while its checkout remains is restored; a backup that names no checkout, in its record or its config's `root:`, is skipped as `gone` unless `--force`) or `failed` (`reason` and `code`: `restore_conflict` with `files`, `workspace_locked`, `backup_symlink`, `error`), plus `backup` (the batch taken of what the restore replaced, reason `restore`; null when nothing was replaced), `restored_from` and `skipped`. A file the batch created is deleted. Status as for `template apply`: `ok`, `partial` (exit 3) or `failed` (exit 1); an unknown ID is `backup_not_found`, a name the batch lacks `unknown_workspace`.

`template adopt [WS...] [--all | --project [NAME]] [--dry-run] --json` prints the action document (`"action":"template adopt"`) with one row per workspace (`workspace`, `outcome`, `reason`, `message`, `match` (`exact` when a render of the template a new config would use today is byte for byte the file, else `approx`; null when nothing was adopted), `kind`, `template`, `code`; a worktree config without its `Worktree — BRANCH (PROJECT)` line is adopted `approx`, the project taken from the name and the branch from the checkout's `.git` HEAD, else its directory name) and the top-level `adopted` counts by `match` (`{}` when none). `outcome` is `adopted` (`would_adopt` under `--dry-run`), `skipped` (`reason` `tracked` for a config that already has a usable render record, `gone` for a config renamed or removed while adopt waited for the lock) or `failed` (`reason` and `code`: `adopt_unrecoverable`, `workspace_locked`, a render error's code). Only the render record is written, never the config. Status as for `template apply`: `ok`, `dry_run`, `partial` (exit 3) or `failed` (exit 1).

## Help pages

`--help --json` (or `--json --help`) on any subcommand or verb prints its help page as one JSON document, made from the text the page prints, so the two say the same. It is not enveloped. It prints the page and does nothing else.

```json
{"usage":["workspace ask list [WS] [--all] [--json]"],"description":"List the open questions.","options":[{"flags":"--all","description":"Include answered ones"}],"examples":[{"command":"workspace ask list","scenario":"open questions of this workspace"}],"sections":[{"heading":"Accepts","text":"..."}]}
```

- `usage`: the usage lines without `Usage:`. `description`: the text between the usage and the first heading. `options`: each flag with its words (`flags`) and text (`description`, continuation lines joined by a space). `examples`: the command and its scenario, split at the `    # ` separator (`scenario` is empty when there is none).
- `sections`: every other headed part (`Accepts:`, `Exit codes:`, `Environment variables:`, the root page's `Subcommands:`) as `{heading, text}`; absent when there is none. A page of another shape still gives valid JSON: what is not recognised stays in `description` or `sections`.
- Only a plain help request is intercepted: before any `--`, a `--json` and a `--help` or `-h`, with no word starting with a dash before the help word. A dashed word could be a flag that takes the help word as its value (`--name --help`), and the flags of a command are not known here, so such a line is left entirely alone, `--json` included, and behaves as it did before. The limit: `plan pause --interrupt --help --json` prints the text page. Put the verb and its arguments first: `plan pause --help --json`.
- Also left alone: `--help` inside one argument (`ask "what does --help --json do"`), after `--`, and in `ask` after words that are not a verb (`ask what is --help --json` is a question, and prints what it always did). A command where `--json` alone is a flag runs as before.
- A help request that fails (`nosuch --help --json`) keeps its exit status and prints the [error envelope](#failure) with code `usage`.

## Failure

```json
{"schema_version":1,"ok":false,"error":"Unknown workspace 'api'","code":"unknown_workspace","details":{"name":"api"}}
```

- `error` is the message a person would read.
- `code` is one of the codes below. A code never changes meaning; renaming or repurposing one is a `schema_version` bump.
- `details` is machine data, present only when the command has some.
- `retry` is present only when a flag turns the refusal into a forced run: `{"flags":["--force"],"destructive":true}`. A temporary failure (`push_network`) gives `{"flags":[],"destructive":false}`: run the same command again. No `retry` means a plain retry is not safe or will not help. Every `push` and `pr create` push error also has `details.permanent` (`true`, or `false` for `push_network` and `push_timeout`); `push_failed` is `permanent: true` because retrying without knowing why is the riskier choice. `push_timeout` has `details.state_unknown: true` and no `retry`: origin may have taken the push, so check with `git ls-remote origin BRANCH` first. "Every push error" means every coded one: the uncoded errors (`git is not installed`, a detached HEAD) have no `permanent`.

To decide after a push failure, read these in order:

| You see | Do |
|---|---|
| `retry` present | Run the same command again. |
| `details.permanent: true` | Stop; retrying will not help. |
| `details.state_unknown: true` | Check the remote (`git ls-remote origin BRANCH`) first, then decide. |

Do not treat `permanent: false` alone as retryable: `push_timeout` is `permanent: false` and has no `retry`.

The exit code is unchanged by `--json` (1 for most failures, 2 for `not_submitted`, 75 for `clear_unconfirmed`).

`--json` is found as its own argument anywhere before a bare `--`, so `workspace parent --json` and `workspace parent --json app` both ask for it, and `workspace run app -- cmd --json` passes `--json` through to the command.

## Never prompting

`--no-input`, or `WORKSPACE_NO_INPUT=1` (empty, `0` and `false` mean off), works on every command and may appear anywhere before a bare `--`. A prompt that would have read stdin fails with `confirmation_required` instead, before anything is printed or read: `details.prompt` is the question and `retry.flags` the flag that answers it (`--force` for `kill`, `cleanup` and `prune`; `--yes` for `projects kill`), with `retry.destructive` true. Prompts with no such flag, like choosing a branch, give no `retry`. Commands that never prompt are unaffected; `session-event` still reads its hook payload from stdin.

## Error codes

| Code | Meaning |
|---|---|
| `error` | Any failure without a more specific code. |
| `usage` | A bad option, a missing or extra argument, or an unknown subcommand. Also, on `workflow status` and `plan status`, more than one of the scope flags `--name`, `--project` and `--all` (and, for `plan status`, `--file` and `--group`), or `workflow status RUN` with a scope flag. |
| `unknown_workspace` | The named workspace isn't known. `details.name`. A workspace name may be the part after `.worktree-` (`y` for `a.worktree-y`); an exact name always wins. A short name that resolves prints one note on stderr, never on a `--json` run. Several matches are `ambiguous_workspace`. Also a `relaunch` name with no config, an unknown `--project NAME`, and a bare `--project` from a workspace that is in no project, on `workflow status` and `plan status`. |
| `ambiguous_workspace` | A short workspace name (the part after `.worktree-`) matches more than one workspace. `details.name`, `details.matches` (sorted full names); give the full name. |
| `workspace_name_case_conflict` | A new workspace would have a name that differs only in case from an existing workspace with a different directory (`add`, `launch PATH`, `start`). `details.name`, `details.existing`, `details.existing_root`. |
| `not_in_workspace` | No workspace could be detected from the working directory. `details.path`. `workflow status` and `plan status` with no scope flag, or with a bare `--project`, outside a workspace; the message names `--name WORKSPACE`, `--project NAME` and `--all`, which answer from anywhere (see [`workflow status`](README.workflow.md#which-runs-status-shows)). |
| `workspace_not_active` | `relaunch` was given a workspace, named or detected from the working directory, that isn't active; checked before anything is stopped. `details.names`. |

| `no_daemon` | No agent daemon is running for the workspace. |

| `unreadable_reply` | The agent daemon's reply couldn't be read. `details.maybe_delivered: true` as for `connection_failed`. |
| `unsaved_work` | The worktree has uncommitted changes or unpushed commits. `details` has the counts; `retry` is `--force`. |
| `unsaved_unknown` | git couldn't tell whether the worktree has unsaved work. `retry` is `--force`. |
| `not_prunable` | prune: a `--name` is not a prune candidate (text mode; with `--json` it is a failed row). `details.names`. |
| `prune_remove_failed` | prune --json: a row's `error` when git refused to remove the worktree (locked, for example). Appears in rows only. |
| `session_running` | remove: the workspace's tmux session is up; stop it first. `details.name`, `details.session`. |
| `not_removable` | remove: the workspace is a worktree project; use `kill`, `finish` or `prune`. `details.name`, `details.root`. |
| `not_submitted` | Text reached the pane but wasn't confirmed submitted; check before resending. |
| `confirmation_required` | A prompt would have read stdin while `--no-input` or `WORKSPACE_NO_INPUT` was set, or `plan delete` was run without `--yes` (`details.name`, `details.path`, `retry.flags` `["--yes"]`). `details.prompt` is the question; `retry` names the flag that answers it, when there is one (`--force` or `--yes`, destructive). |
| `no_session` | The workspace has no running tmux session. `details.workspace` (from `send`, `focus --pane`, `ask answer --deliver`, `agent-run restart`, `handoff`). |
| `bad_keys` | `agent-run send --keys` named something that isn't a tmux key name, or too many keys. `details.keys`. |
| `no_pane` | The question wasn't asked from a tmux pane, so `ask answer --deliver` has nowhere to type (`details.question`); or `agent status post` was run outside a tmux pane (`$TMUX_PANE` unset). |
| `stale_pane` | `ask answer --deliver` can't be sure the question's pane is the one that asked: tmux restarted since, or the question was recorded without the tmux server. `details.question`, `details.pane`. |
| `focus_failed` | tmux couldn't select the pane for `focus --pane`; the window is already in front. `details.pane`, `details.workspace`, and `details.warnings` when a `focus.chain` step failed. |
| `saved_window_offscreen` | `launch` found a saved window position on no connected screen and tiled the window instead. A warning on stderr (`Warning: saved_window_offscreen: ...`) and in `--json` `warnings`, never an error. |
| `window_position_unreadable` | `launch` could not read a workspace's `window.json`, tiled the window instead and left the file alone. A warning on stderr and in `--json` `warnings`, never an error. |
| `launcher_pane_missing` | `launch` still had no iTerm pane for a workspace after one retry. Reported as a warning on stderr (`Warning: launcher_pane_missing: Failed to create panes for: ...`), never an error; that workspace is not started in a pane. |
| `no_window` | `focus` found no iTerm window recorded for the workspace. `details.workspace`. |
| `no_windows_to_cycle` | `focus --cycle` found no tracked workspace with a live iTerm window. |
| `window_gone` | `focus` found that the recorded iTerm window no longer exists. `details.workspace`, `details.iterm_window_id`. |
| `no_screen_geometry` | `focus --center` could not read the connected screens, so the window could not be centered. `details.workspace`, `details.iterm_window_id`, and `details.warnings` when a `focus.chain` step failed first. |
| `checkout_missing` | The workspace's checkout directory no longer exists. |
| `config_parse` | A config file exists but can't be parsed as a YAML mapping. `details.path` and `details.reason`. |
| `unknown_config_key` | `config set`, `get`, `unset` or `show <key>` was given a key that is not a config key, or `config keys QUERY` matched no key. `details.key`. (Before this code existed these commands reported `usage`; the exit code is still 1.) |
| `scope_not_allowed` | `config set`, `get` or `unset` named a `--scope` the key doesn't allow (a global-only key at `project`, a project-only key at `workspace` in a worktree, ...). `details.key`, `details.scope` (the scope as typed) and `details.allowed`, the scopes the key does allow, lowest first (`global`, `project`, `workspace`). Nothing is written. |
| `agent_command_not_executable` | `config set agent.commands.<kind>` was given a command whose program is an absolute path that does not exist (`missing`), is not a regular file (`not_a_file`) or is not executable (`not_executable`). `details.path`, `details.reason`. | `editor_failed` | `config edit` or `template edit` could not open the editor: `$VISUAL` or `$EDITOR` is not a valid command (an unbalanced quote), or the editor could not be run or exited non-zero. `details.path` is the file to edit by hand. |
| `notes_dir_unresolved` | `notes dir` (and `handoff new` with no doc given) can't work out the directory: the project's `notes.default_dir` rule uses `{branch}` and the checkout is on a detached HEAD. `details.name`, `details.path` (the checkout). |

| `invalid_group_name` | `projects group create`: the name has no letters or digits, has a control character, or makes a slug over 64 characters. `details.name`. |

### promote codes

`promote` refuses before it changes anything, except `move_failed` (undone) and `move_incomplete` (kept under a ref). Reused codes: `rebase_in_progress`, `usage`, `config_parse`, `unknown_workspace`. A `start` failure after the move carries `start`'s own code with `details.moved` and `details.next` (`["workspace start BRANCH"]`, which adopts the worktree). A Ctrl-C, SIGTERM or SIGHUP during the move waits for the git step under way to end, then the move is undone; one that comes in the moment after the work is safe in the worktree (while the snapshot ref is deleted) stops promote there, before the workspace is made and with no document: `workspace start BRANCH` finishes it.

### rename codes

`rename` refuses before it changes anything, except `rename_failed` (undone) and `rename_incomplete` (finish it by running the same command). Reused codes: `unknown_workspace`, `checkout_missing`, `detached_head`, `rebase_in_progress`, `workspace_name_case_conflict`. `details.workspace` and `details.branch` are the current names; the new ones are `details.new`, or `new_workspace`, `new_branch` and `new_path` in `rename_target_taken`. `details.fix`, where listed, is a command that clears the refusal.

| Code | Meaning |
|---|---|
| `workspace_running` | The workspace is not stopped: its tmux session or agent daemon is running. Run `workspace stop NAME` first. `details.workspace`, `details.session`, `details.reason` (`session` or `agent`), `details.fix` (`workspace stop NAME`). |
| `run_active` | A workflow run is still going on the checkout, a gate wait included. `details.run_id`, `details.path`. |
| `dev_lock_held` | The checkout holds the `devenv` lock. Run `workspace dev down` first. `details.path`, `details.workspace`, `details.fix` (`workspace dev down NAME`). |
| `rename_main_checkout` | The workspace is a main checkout. `details.workspace`, `details.path`. |
| `rename_not_worktree` | The workspace's name has no `.worktree-` part, or its checkout is not a linked worktree. `details.workspace`, `details.path`. |
| `rename_pull_request_branch` | The branch, or the new name, is a `pr-N` branch. `details.branch`, `details.new`. |
| `rename_no_change` | The branch already has that name. `details.branch`. |
| `rename_invalid_name` | The new name is not a branch name git accepts, leaves no directory name, or makes a config file name (`workspace.<name>.yml`) over 255 bytes. `details.new`; for the length `details.reason` (`too_long`), `details.bytes`, `details.limit`. |
| `rename_target_taken` | A new name is taken. `details.taken`: any of `branch`, `branch_conflict` (a branch that can't coexist with the new name as a git ref, `a` and `a/b`; `details.conflicting_branch`), `directory`, `config`, `state_key`, `state_dir`, `project_settings`, `socket`, `agent_log`, `inbox`, `hook_events`, `session` (the new tmux session name), `notes_target` (`details.notes_path`); `details.new_workspace`, `details.new_branch`, `details.new_path` (always the new checkout path), `details.paths` (the files in the way, by what is taken), `details.fix` (the `rm` command, when only `agent_log`, `socket` or `hook_events` are in the way). |
| `rename_case_only` | The new worktree directory differs from the old one only in case, which the file system may not move. `details.from`, `details.to`. |
| `rename_locked_worktree` | The worktree is locked (`git worktree lock`). `details.path`, `details.fix` (`git worktree unlock PATH`). |
| `rename_in_progress` | An earlier rename was started and not finished; run the same command again to finish it. `details.workspace`, `details.new_branch` (the name that rename was for), `details.rerun` (`true`), `details.fix` (the command). | `rename_notes_other_volume` | The notes would move to another volume, which a rename can't do. `details.workspace`, `details.new`, `details.from`, `details.to`. |
| `rename_failed` | A git step failed and was undone, or the rename could not begin. Nothing changed and no journal is left. `details.workspace`, `details.new_branch`, `details.step` (`startup_lock`, `journal`, `worktree_move`, `branch_rename`), `details.rolled_back`, `details.signal` when a signal stopped it. |
| `rename_incomplete` | The rename stopped after the git steps, or the undo of one failed. The journal is kept; the same command finishes it. `details.workspace`, `details.new_workspace`, `details.new_branch`, `details.failed` (the steps; `startup_lock` on a re-run that could not take it), `details.problems`, `details.rerun` (`true`, or `false` when no config is left under either name and a re-run can not finish), `details.fix` (the command, or the `rm` of the journal), `details.signal` when a signal stopped it. |

The plan (`rename --dry-run --json`, from `RenamePlan::Plan#to_h`) has these fields:

| Field | Meaning |
|---|---|
| `project` | The main project's name. |
| `workspace`, `branch`, `path`, `session` | Each an object `{from, to}`: the value now and after. `path.to` equals `path.from` when only the branch changes. |
| `notes` | `{action, from, to, reason}`. `action`: `move` (a directory of its own goes from `from` to `to`), `with_checkout` (inside the checkout, goes with it) or `stays`. `reason` is null unless `action` is `stays`: `custom` (not where the rule puts it), `same` (the rule gives the same directory under the new names), `nested` (the new place is inside the old one or the other way round) or `unresolved`. |
| `warnings` | The list below, each `{code, message, ...}`. |
| `resume` | `true` when the plan was made for a re-run that finishes a half-done rename. |

`rename` puts these in `warnings[]` as `{code, message, ...}`; none is an error envelope's code.

| Code | Meaning |
|---|---|
| `upstream_other_name` | The branch keeps tracking a remote branch under the old name; `push` will refuse (`push_rejected`, `details.reason` `upstream_mismatch`) until it is renamed or unset. `upstream`. |
| `prune_pull_request` | `prune` looks a pull request up by the local branch name and will not find one opened from the old remote branch. `branch`. |
| `transcript_not_continued` | Claude Code keeps the checkout's conversations under its old path, so `launch` starts a new one; `restore` resumes. `path`. |
| `notes_unresolved` | The notes directory could not be worked out, so the rename leaves it. `problem` (the resolver's code and message, or null). |
| `notes_nested` | The notes stay where they are: the new location is inside the old one or the other way round. `path`. |
