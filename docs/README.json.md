# `--json` output

Every command that takes `--json` prints exactly one JSON value on stdout, and with `--json` nothing is written to stderr for a failure. A failure (refusal, usage error, unknown subcommand) is always the error envelope below. Success is an enveloped object for every command except three, which print their bare document under `--json` and the envelope under `--json-envelope`; see [Success output without the envelope](#success-output-without-the-envelope).

## Success

```json
{"schema_version":1,"ok":true,"workspaces":[],"warnings":[]}
```

`schema_version` and `ok` come first, then the command's own keys (see each command's page).

### Success output without the envelope

With `--json` these commands keep their original success shape, which other tools already parse. Their failures use the envelope with either flag, so check for `ok` being `false` before reading the success shape. `--json-envelope` (it implies `--json`) opts in to the envelope for one call.

| Command | Success shape |
|---|---|
| `list --json` | A bare array: names, or objects with `--show-urls`, `--liveness` or `--all`. |
| `status --json` | A bare object keyed by project name (`{}` when nothing is tracked). |
| `parent --json` | A bare object with `name`, `path`, `git_common_dir`, `is_worktree`, `worktree`; no `schema_version` or `ok`. |

| Command | With `--json-envelope` |
|---|---|
| `list` | `{"schema_version":1,"ok":true,"workspaces":[...],"warnings":[]}`; `workspaces` is the array `--json` prints (also with `--all`, `--show-urls`, `--liveness`). |
| `status` | `{"schema_version":1,"ok":true,"status":{...},"warnings":[]}`; `status` is the object `--json` prints. |
| `parent` | `{"schema_version":1,"ok":true,"parent":{...},"warnings":[]}`; `parent` holds `name`, `path`, `git_common_dir`, `is_worktree`, `worktree`. |

`warnings` is always a list (empty today). The bare `--json` default stays until a later major version. It is a per-call flag, not a config key, so a caller states which shape it parses in the command itself.

To ask which of these a given CLI supports, run `workspace capabilities --json` (see [capabilities](README.capabilities.md)). The shared scope rule for `workflow status` and `plan status`, `--project` included, needs `workflow` 9 and `plan` 6. `workflow status --table` and the `worktree` field need `workflow` 10. The documents themselves are the same as before.

## Actions

These commands take `--json` and print one action document: `add`, `launch`, `stop`, `kill`, `relaunch`, `restore`, `focus`, `repair`, `cleanup`, `deactivate`, `reactivate`, `dev up`, `dev down`, `dev wait`, `dev leave`, `lock release`, `config set`, `config unset`, `config edit`, `daemon restart` (also with `--all`), `agentd restart`, `pipeline start`, `pipeline advance`, `pipeline reset`, `prune`, `ui open`, `binding set`, `binding show`, `binding clear`, `library add`, `library update`, `library remove`, `workflow add`, `workflow update`, `workflow remove`, `workflow run`, `workflow start`, `workflow sweep`, `workflow sweep --install`, `workflow sweep --uninstall`, `workflow sweep --installed`, `workflow resume`, `workflow cancel`, `workflow approve`, `workflow reject`, `go` and `step done`. (`finish`, `start`, `lock clear` and `projects stop|kill` have their own pages; `projects stop|kill` use the same shape.) `start --recipe` with a recipe that names a workflow prints this action document, with action `start` and `recipe` (`ref`, `scope`) in the row, in place of the `start` document. `library_recipes` 2 in `capabilities --json` says a CLI does this.

```json
{"schema_version":1,"ok":true,"action":"stop","status":"ok",
 "results":[{"workspace":"api","outcome":"stopped","reason":null,"message":null}],
 "warnings":[],"summary":{"stopped":1}}
```

- `action` is the command's words: `launch`, `dev up`, `lock release`, `config set`, `config edit`, `pipeline start`.
- `results` has one row per target with `workspace` (null when the command has none, such as a global `config set`), `outcome`, `reason` (a short machine-readable cause, or null) and `message`. A row may carry more keys, named on the command's page (`iterm_window_id` for `launch` and `focus`, `play` for `launch --play`, `prompt_sent` and `pane` for `launch` and `pane` for `run --json`, `key`, `value`, `global`, `scope`, `layer`, `file`, `comments_preserved`, `effective` and, only when non-empty, `warnings` for `config set`, the same without `value` for `config unset` (whose `outcome` is `unset`, or `noop` when the key was not set in that file and nothing was written), `effective` keeping the type `config show` uses for the key (a number may be a float, a boolean may be a string), `work_item_ref` for `pipeline`, `run` for `workflow`, and `run_id`, `step`, `attempt` and `reported` for `step done`).
- `outcome` is per command (see its page). `failed` and `refused` count as failures.
- `status` is `ok` (no row failed), `partial` (some did), `failed` (all did, or the command exited non-zero), `cancelled` (a prompt was declined; nothing changed), `dry_run` (`--dry-run` reported the plan; nothing changed), or `refused` (a preflight check refused every target; nothing changed).
- `ok` is `true` for every action document, including `failed`: it means the command ran and reports per-row outcomes. Check `status` and the exit code. A refusal or usage error is the failure envelope above, with `ok: false`.
- `summary` counts rows by `outcome`. `warnings` is a list of strings, each a sentence for a person to read; it is empty when there is nothing to say.
- `rebase --json` is a single result document, not an action document: it exits 0 for every `outcome`, `conflict` and `default_not_updated` included, so a script must read `outcome`. An error (the envelope above) exits 1. When git runs past its time limit during the rebase, the rebase is aborted and the error carries `details.aborted: true` (code `error`); if the abort fails, the code is `rebase_in_progress` with `details.aborted: false`.
- The exit code is 0 for `ok`, `cancelled` and `dry_run`, 3 for `partial`, and 1 for `failed` and `refused`, except that a command that exits with its own code (`dev up` exits 75 after `--max-wait`, `dev wait` after its own) keeps it.
- The progress text a command prints goes to stderr, so stdout holds the one document. A command that reports only an exit code (`dev up`, `dev down`, `dev wait`, `lock release`) gives a `failed` row with `reason: "exit_code"` and `exit_code`; the explanation is on stderr.
- `dev up --json` still runs the project's `pre_dev_up` and `post_dev_up` hooks; their output goes to stderr with the progress text, and stdout keeps the one JSON document (unlike `finish --json`, which skips the `post_kill` hook). See [`dev`](README.dev.md#hooks).
- `focus` puts a sentence in `warnings` for each `focus.chain` step that failed or could not be read, and for a failed `--highlight`; the row is still `focused`. The two errors that can follow the chain, `no_screen_geometry` and `focus_failed`, carry the same sentences in `details.warnings` (absent when there are none). See [`focus`](README.focus.md#focus-chain).
- `kill` adds `"notes_inside_worktree":{"dir":"/abs","files":3}` to its row, and a sentence to `warnings`, when the workspace's notes directory was inside the removed worktree and held files; the key is absent otherwise. `kill` also adds `"dev_stopped": true` to its row when it stopped the worktree's dev environment first; the key is absent otherwise. `kill` always adds `"branch":{"name","deleted","kept_reason"}` to its `killed` row, and `"remote_branch":{"name","remote","deleted","kept_reason"}` with `--delete-remote` (see [`kill`](README.kill.md#branches)). `finish` and `start` have their own pages (`finish` has both keys at the top level; `start` gains `notes_dir` and, when the project's `start.copy_files` applied, `copy_files` with the checkout-relative paths it copied and skipped).
- `config edit --json` opens no editor. Its one row has `outcome: "ready"`, `workspace` (the name whose file it is, null for the global file), `global`, `scope`, `layer`, `file` (the path) and `created` (true when the file was absent and a comment-header stub was written). See [`config`](README.config.md#config-edit).
- `kill` ends the tmux session last. Run it from outside the session it kills, or the process can end before the document prints.
- `stop` with `--json` does not warn about a named workspace that isn't active; it gives that workspace a `not_running` row. When iTerm2 does not answer within 5 seconds, `stop` still stops the workspace and leaves its window open; `warnings` says so.
- `agent run --json` is not an action document. It prints `{"schema_version":1,"ok":true,"workspace":"api","work_item_ref":"wi_12","dispatch_id":"agent-run-ab12cd34","dry_run":false,"reply":{...}}`, where `reply` is the agent's reply as is, including its own `ok`. The exit code is 0 whatever the reply says; read `reply.ok`. With `--dry-run` there is `message` (what would be sent) and no `reply`.

## Workflow status rows

`workflow status --needs-me --json` prints `{"schema_version":1,"ok":true,"generated_at":...,"status":"ok","unreadable":0,"runs":[...],"warnings":[]}`: one row per run waiting for a person, longest wait first; `status` is `partial` and the exit code 3 when `unreadable` run files were left out (`run`, `workflow`, `workspace`, `step`, `attempt`, `code`, `kind`, `gate_file`, `detail`, `since`, `waiting_seconds`, `next_action`, `actions`), `runs` empty and exit 0 when none is and every file was read; `next_action` is for a person, never to run unattended; `--all`, `RUN` and `--table` with it are `usage`. See [what needs you](README.workflow.md#what-needs-you). `workflow status --table --json` prints `{"schema_version":1,"ok":true,"generated_at":...,"rows":[...],"warnings":[]}`: one row per run, with `id`, `workflow`, `state`, `step` (`null` once the run has finished), `workspace`, `workspace_status` (`live`, `stopped`, `gone` or `unknown`), `agent` (`working`, `waiting`, `idle` or `null`), and `has_config`, `has_tmux_session`, `has_worktree`, `has_state_dir` (`true`, `false`, or `null` when it could not be read). The workspace fields describe the workspace now, not when the run ran. See [the status table](README.workflow.md#the-status-table).

`workflow check ID STEP --json` prints `{"schema_version":1,"ok":true,"workflow","step","worktree","passed","command","exit_code","timed_out","error","timeout","duration","log","artifacts","artifacts_created","base_sha","tail","warnings"}` after running the step's `status:` command once, outside any run (no run file, event or lock); `ok` says the check ran and `passed` how it ended, and the exit status is 1 when `passed` is false (needs `workflow` 26; see [trying a check](README.workflow.md#trying-a-steps-check)).

`workflow render ID STEP --json` prints `{"schema_version":1,"ok":true,"workflow","step","workspace","worktree","inputs","gate","packs","instructions_path","previews":[{"name","value"}],"warnings":[{"code","message"}],"text"}` and writes nothing; `previews` are the placeholder values that belong to a run that does not exist (`run`, `artifacts`, and `workspace` outside any workspace), `warnings` has `not_in_checkout` outside a git checkout, `text` is the composed instructions; a missing required input is `input_required`, an unknown step `unknown_step` (see [rendering](README.workflow.md#rendering-a-steps-instructions); needs `workflow` 25).

`workflow simulate ID --script FILE --json` prints `{"schema_version":1,"ok":true,"workflow","script","inputs","outcome","stopped","capped","max_actions","actions","run":{"state","current","reason","loops"},"steps":[{"id","state","attempts":[{"n","outcome","code"}]}],"budget","transitions":[{"n","at","type",...}]}`; `outcome` is `completed`, `failed`, `cancelled`, `stopped` (waiting for a person) or `capped` (cut off after `max_actions`). It makes no run and writes nothing outside a temporary directory, and answers `invalid_workflow` when writing there fails (a full disk, or `produces: [x, x/y]`); a simulated stop is exit 0. Needs `workflow` 26.

`workflow sweep --install`, `--uninstall` and `--installed --json` print the action document with one result (`outcome`, `message`, `path`, `label`; `--installed` adds `installed`, `ours`, `loaded` (true, false or null: null means `launchctl` could not answer, exit stays 0, and a script must treat it as unknown, not false), `up_to_date`, `stale`, `interval`, `ruby`, `program`; see [running the sweep on a schedule](README.workflow.md#running-the-sweep-on-a-schedule); needs `workflow` 16). `workflow sweep --json` prints the action document with one result for each run looked at (`outcome`, `reason`, `message`, `run_id`, `step`, `attempt`, `cause`, `action`; see [sweeping stopped runs](README.workflow.md#sweeping-stopped-runs); needs `workflow` 15; outcome `redelivered`, with `cause` `undelivered` and `action` `redeliver`, is a step's undelivered line typed again, needs `workflow` 17, and the failed attempt then carries `redelivered: true` in the run file and does not count against `max_attempts`; outcome `retried`, with `cause` `retry_backoff` and `action` `retry`, is an `on_fail` retry started after its `backoff`, and a run still waiting is `nothing` with `reason` `backoff` and the same `cause`; needs `workflow` 18): status `dry_run` under `--dry-run`, otherwise `ok` unless a result is `failed` (a daemon that could not be started, an interrupt that failed, a missing program, an unreadable run file): `partial`, exit 3, or `failed`, exit 1, when all did; `summary` counts the results by outcome. A failed step the sweep timed out has `details.code` `step_timed_out`. A failed step waiting out an `on_fail` `backoff` reads `state` `waiting` with the reason `retry_backoff` (`details`: `step`, `attempt`, `to`, `until`, `seconds`, `loops`; actions `workflow resume`, which starts the retry now, and `workflow cancel`); the run file holds `backoff` (`until`, `to`, `context`, `text`) until it starts, and no `backoff` key in a run stored before this (needs `workflow` 18). Attempts are not listed in `workflow status --json`; `workflow attempts RUN --json` prints them (see [reading a run's attempts](README.workflow.md#reading-a-runs-attempts); needs `workflow` 12). `workflow stats ID --json` prints the per-step figures of a workflow's runs (`{"schema_version":1,"ok":true,"workflow":ID,"status":"ok"|"partial","last","since","workspace","project","definition","runs","unreadable","undated","unattributed_resumes","steps":[{"step","attempts","passed","failed","not_delivered","unfinished","median_seconds","resumes","tokens_from_unfinished","tokens":{"mean","runs_counted","runs_uncounted"}}]}`; `status` `partial` with exit 3 when a run file could not be read; a null `tokens.mean` means no run recorded tokens, never zero; see [step statistics](README.workflow.md#step-statistics); needs `workflow` 23). `workflow compare ID --json` prints the runs in groups (`{"schema_version":1,"ok":true,"workflow":ID,"status":"ok"|"partial","last","since","workspace","project","by","runs","matched","without_pack","no_attempts","unreadable","undated","warning","groups":[{"sha","runs","settled","first_try","pass_first_percent","running","cancelled","resumes","resumes_per_run"}]}`; `warning` is always present, `partial` with exit 3 as for stats; a bad `--by` is a usage error; see [comparing runs](README.workflow.md#comparing-runs); needs `workflow` 24). `workflow audit RUN --json` prints `{"schema_version":1,"ok":true,"run":ID,"step":STEP-or-null,"clean":bool,"counts":{},"directory":...,"files":[...],"without_evidence":[...]}` and exits 1 (the document still printed, `ok` true) when `clean` is false: a kept copy changed, is missing or was replaced (see [auditing a run's evidence](README.workflow.md#auditing-a-runs-evidence); needs `workflow` 14). The run file keeps each attempt's `head`, `definition_sha256`, `prompt_sha256`, `packs`, `outputs`, `check.command`, `session`, `agent`, `usage` (a main-thread count, null rather than an undercount), `evidence` (the copies of the prompt, check log and outputs kept in the state directory, with their hashes; needs `workflow` 13) and `reasons` (the run file's own `reasons` list holds the waits outside any attempt, each with a `step`; join them to attempts by `step` and time) (see [what an attempt records](README.workflow.md#what-an-attempt-records)).

Each step row of `workflow status --json` has `gate_note`, the text given to `approve` or `reject` with `--note` (or `null`), beside `gate_file` and `note_changed`. `worktree`, the checkout path stored with the run (or `null`), is on every row of `workflow status --json` and on the `run` object of every `workflow` action document. Both need `workflow` 10.

A failed step whose `on_fail` retry waits out a `backoff` has the run file's `backoff` (`until`, `to`, `context`, `text`, and `pane` and `identity`, the pane the run was in and its session and slot) and the reason `retry_backoff`. When the retry came due and that pane was no longer the run's, `backoff.blocked` is `pane_has_run`, `pane_gone` or `pane_changed`, nothing was typed, and the run reads `waiting` with the reason `waiting_you` (`details.kind` `dispatch`, `details.error` the same code; `pane_gone` for a gone pane), whose `actions` are `workflow resume` (needs `--pane`) and `workflow cancel`. `workflow resume --pane PANE` with another agent pane starts the retry. `workflow sweep` reports such a run as `nothing` with `reason` `retry_blocked`, which is not a failure. `workflow resume` (without `--pane`) of a held wait starts nothing and writes no rebind, note or `run_resumed` event; repeating it changes nothing, except that a hold whose cause or pane changed since is recorded once (a new reason and one `step_retry_blocked` event) and returns the result outcome `unchanged` (`message` "Nothing was done: ..."), which is not a failure: exit status 0, with `--json` too. `reason` and `message` of that result, and `workflow status --json` (the run's `reason` with `details.error`, and the run file's `backoff.blocked`), tell a script why. The outcome `unchanged` is also what `workflow resume` answers when an agent is still working on the step or a check is running.

`workflow show ID --json` and `workflow validate --json` add `workflow.extends` when the definition has `extends:`: the parents nearest first, each `{"id","source","path","sha256"}` (the parent file's text digest); the key is absent otherwise. `workflow.sha256` stays the file's own; `workflow.resolved_sha256` (always present) is the digest a run started now would store as `definition_sha256`, which covers the parents too. A parent that can't be used is reported alone, each problem prefixed `extends ID (PATH):`. `workflow add`, `update` and `remove` rows gain `extended_by` (ids of the definitions that extend the one changed, with `ID (project NAME)` for a project's) only when there are some, with a stderr warning. A bad `extends:`/`replace:` is `invalid_workflow` with every problem in `details.problems`.

`workflow validate --json` adds a top-level `warnings` array beside `workflow` (empty when there are none); `workflow.scope` is `project`, `global` or `builtin` when the PATH sits in that definitions directory, else `null` (`workflow.source` stays `file` or `stdin`). Each entry is `{"code":CODE,"step":STEP_ID,"message":TEXT}`. `step_without_proof`: a step with no `produces`, `status`, `require` or `gate` passes on any turn end. `on_timeout_without_timeout`: a step sets `on_timeout: interrupt` or `fail` with no `timeout`. `on_fail_exceeds_max_attempts`: the retries of a step's `on_fail.max` can't all start under `max_attempts`. `unknown_pack`: an `include:` names a pack the library can't find from the current project (`step` is `null` for the workflow's own). `command_unset`: a step needs `commands.test` or `commands.lint` and the project has none. A top-level `not_checked` array (same entry shape; codes `pack_not_checked`, `commands_not_checked`) lists what the last two could not check: outside a git checkout, or (`commands_not_checked` only) when the project's config file does not parse. Warning codes are an open set: callers ignore codes they do not know. Only `workflow validate` reports warnings; `show`, `start` and `run` do not. A warning is not an error code: `ok` stays `true` and the exit code 0. See [Validating a definition](README.workflow.md#validating-a-definition).

## Snapshot

The agent daemon's pane list (`sessions --json`) carries a boolean `turn_failed` per pane, `true` while the agent's last turn stands as ended by an API error (see [`sessions`](README.sessions.md), and [`agentd`](README.agentd.md#recovering-from-an-api-error) for the recovery). The panes of `snapshot --json` don't list it.

The same pane list carries `waits` per pane: every open wait as `agent_id`, `tool`, `input` and `since` (the main agent's `agent_id` is `null`). `input` is as sensitive as `waiting_input`, and the panes of `snapshot --json` leave `waits` out (see [`sessions`](README.sessions.md)).

`snapshot --json` prints one read-only document of everything a UI polls (see [`snapshot`](README.snapshot.md)). `--json` is required; a source that can't answer is reported as unavailable (null fields, `daemons_unavailable` rows, `warnings`) rather than as clean, and the command still succeeds. Its `cursor` is `ev:<inode>:<byte offset>` of the event log.

`ui status --json` prints one read-only document: `{"schema_version":1,"ok":true,"running","pids","handler","links","probe","warnings"}`. It opens nothing. A probe that cannot answer is `ok: true`, exit 0, with `running`, `pids` and `handler` null and `probe` naming the problem; a usage error is the error envelope (see [`ui`](README.ui.md#status)).

## Goal

`goal show [REF] --json` prints `{"schema_version":1,"ok":true,"goal":{...},"warnings":[]}` and `goal list [--all] --json` prints `{"schema_version":1,"ok":true,"goals":[...],"warnings":[]}`. Both are read-only; a source that can't answer is a null level plus a warning. `show` also carries `done_means` and `not_yet` (lists of `{code, text}`) and `delivery`, and `list` rows `delivered` and `not_yet_codes`: a finished plan or spine is `done` only once the branch's commits are on the default branch (local git only). Every field, the closed value sets, nullability and warning codes are in [README.goal.md](README.goal.md).

## Tmuxinator templates

`template list [--scope SCOPE] [--name WS] --json` prints `{"schema_version":1,"ok":true,"workspace":...,"selected":{"project":{...},"worktree":{...}},"templates":[...],"warnings":[]}`. Each `templates` row has `name`, `ref`, `scope`, `project`, `description`, `path`, `files`, `effective` and `selected_for` (the kinds, `project` and `worktree`, that render from it for that workspace). `selected.<kind>` is `{name, scope, source}`, or null with a warning (`code`, `kind`, `message`) when the set it names can't be found; an edited copy `init` installed shows as the set `legacy`. `template show [NAME] --json` prints `{"schema_version":1,"ok":true,"templates":[...],"warnings":[]}` with one row per file (`kind`, `template`, `scope`, `source`, `path`, `content`, `sha256`), and `template path --json` the same rows without `content` and `sha256`. `source` is where the set's name came from (`worktree`, `project`, `global`, `default`, `legacy`), or `argument` when NAME was given. All three read only. `template variables [--kind K] [--name WS] --json` prints `{"schema_version":1,"ok":true,"variables":[...],"warnings":[],"workspace":...}`; each row has `name`, `kinds`, `required` (per kind), `description`, `source`, `sample`, `whole_line` and, with `--name`, `value` (null when the record holds none), and `value_state` (`recorded`, `no_record`, or null without `--name`) is set at the top; `value` is what `render --name` would fill (the agent command from current settings, `PRE_WINDOW` as its line or `(dropped)`). `template render ... --json` prints `{"schema_version":1,"ok":...,"template":...,"source":...,"path":...,"kind":...,"workspace":...,"inputs":{...},"content":...,"diff":...,"warnings":[...]}`: `template` is the set's name (null for `--file`), `content` the filled text (null when the renderer refused), `diff` the unified diff under `--diff` (with `changed`, true or false, only then), and `warnings` the file's problems (`severity`, `code`, `kind`, `message`); `ok` is false, and the exit status 1, when one is an error. Neither writes anything; a workspace with no render record is `no_render_record` for `render --name`.

`template validate [NAME | --file F] --json` prints `{"schema_version":1,"ok":...,"files":[{"kind","template","path","problems":[{"severity","code","kind","message"}]}],"errors":N,"warnings":N}` (`template` is null for `--file`). It is not an error envelope: a problem is reported in the document, with `ok` false and exit 1 when any is an error, and `ok` true and exit 0 for warnings alone. `template diff [NAME] [--against NAME] --json` prints `{"schema_version":1,"ok":true,"files":[{"kind","template","path","against_path","changed","diff"}],"warnings":[],"against":NAME,"changed":bool}`; it always exits 0, `warnings` is always empty, and `diff` is the unified text, empty when the files are the same.

`template new NAME`, `template edit [NAME]` and `template use NAME` change something, so under `--json` each prints the action document (`{"schema_version":1,"action":"template new"|"template edit"|"template use","status":...,"results":[row],...}`) and exits through its `status`. The `new` row has `outcome: "created"`, `template`, `scope` (`global` or `project`), `path`, `from` (the set copied) and `warnings` (the copy's problems, as in `validate`, and a `shadows_template` entry with the hidden set's `scope` for each lower-scope set of the same name the copy now hides); a name already in that scope is `template_exists`, an invalid source `invalid_template`. The `edit` row has `outcome` `edited`, or `failed` with `reason: "invalid_template"` (exit 1) when a file has an error, `template` and `files` (`kind`, `template`, `path`, `problems`); `--json` opens no editor and checks the files as they are, and a built-in set is `template_builtin_readonly`. The `use` row has `outcome: "selected"`, `template`, `key` (`tmuxinator.template`, or `tmuxinator.worktree_template` with `--kind worktree`), `layer` and `file`; a name no set has is `unknown_template`.

## Help pages

`--help --json` (or `--json --help`) on any subcommand or verb prints its help page as one JSON document, made from the text the page prints, so the two say the same. It is not enveloped. It prints the page and does nothing else.

```json
{"usage":["workspace ask list [WS] [--all] [--json]"],"description":"List the open questions.","options":[{"flags":"--all","description":"Include answered ones"}],"examples":[{"command":"workspace ask list","scenario":"open questions of this workspace"}],"sections":[{"heading":"Accepts","text":"..."}]}
```

- `usage`: the usage lines without `Usage:`. `description`: the text between the usage and the first heading. `options`: each flag with its words (`flags`) and text (`description`, continuation lines joined by a space). `examples`: the command and its scenario, split at the `    # ` separator (`scenario` is empty when there is none).
- `sections`: every other headed part (`Accepts:`, `Exit codes:`, `Environment variables:`, the root page's `Subcommands:`) as `{heading, text}`; absent when there is none. A page of another shape still gives valid JSON: what is not recognised stays in `description` or `sections`.
- Only a plain help request is intercepted: before any `--`, a `--json` and a `--help` or `-h`, with no word starting with a dash before the help word. A dashed word could be a flag that takes the help word as its value (`--name --help`), and the flags of a command are not known here, so such a line is left entirely alone, `--json` included, and behaves as it did before. The limit: `plan pause --interrupt --help --json` prints the text page. Put the verb and its arguments first: `plan pause --help --json`.
- Also left alone: `--help` inside one argument (`ask "what does --help --json do"`), after `--`, and in `ask` after words that are not a verb (`ask what is --help --json` is a question, and prints what it always did). A command where `--json` alone is a flag runs as before.
- A help request that fails (`nosuch --help --json`) keeps its exit status and prints the [error envelope](#failure) with code `usage`.

## Failure

```json
{"schema_version":1,"ok":false,"error":"Unknown workspace 'api'","code":"unknown_workspace","details":{"name":"api"}}
```

- `error` is the message a person would read.
- `code` is one of the codes below. A code never changes meaning; renaming or repurposing one is a `schema_version` bump.
- `details` is machine data, present only when the command has some.
- `retry` is present only when a flag turns the refusal into a forced run: `{"flags":["--force"],"destructive":true}`. A temporary failure (`push_network`) gives `{"flags":[],"destructive":false}`: run the same command again. No `retry` means a plain retry is not safe or will not help. Every `push` and `pr create` push error also has `details.permanent` (`true`, or `false` for `push_network` and `push_timeout`); `push_failed` is `permanent: true` because retrying without knowing why is the riskier choice. `push_timeout` has `details.state_unknown: true` and no `retry`: origin may have taken the push, so check with `git ls-remote origin BRANCH` first. "Every push error" means every coded one: the uncoded errors (`git is not installed`, a detached HEAD) have no `permanent`.

To decide after a push failure, read these in order:

| You see | Do |
|---|---|
| `retry` present | Run the same command again. |
| `details.permanent: true` | Stop; retrying will not help. |
| `details.state_unknown: true` | Check the remote (`git ls-remote origin BRANCH`) first, then decide. |

Do not treat `permanent: false` alone as retryable: `push_timeout` is `permanent: false` and has no `retry`.

The exit code is unchanged by `--json` (1 for most failures, 2 for `not_submitted`, 75 for `clear_unconfirmed`).

`--json` is found as its own argument anywhere before a bare `--`, so `workspace parent --json` and `workspace parent --json app` both ask for it, and `workspace run app -- cmd --json` passes `--json` through to the command.

## Never prompting

`--no-input`, or `WORKSPACE_NO_INPUT=1` (empty, `0` and `false` mean off), works on every command and may appear anywhere before a bare `--`. A prompt that would have read stdin fails with `confirmation_required` instead, before anything is printed or read: `details.prompt` is the question and `retry.flags` the flag that answers it (`--force` for `kill`, `cleanup` and `prune`; `--yes` for `projects kill`), with `retry.destructive` true. Prompts with no such flag, like choosing a branch, give no `retry`. Commands that never prompt are unaffected; `session-event` still reads its hook payload from stdin.

### promote codes

`promote` refuses before it changes anything, except `move_failed` (undone) and `move_incomplete` (kept under a ref). Reused codes: `rebase_in_progress`, `usage`, `config_parse`, `unknown_workspace`. A Ctrl-C, SIGTERM or SIGHUP during the move waits for the git step under way to end, then the move is undone; one that comes in the moment after the work is safe in the worktree (while the snapshot ref is deleted) stops promote there, before the workspace is made and with no document: `workspace start BRANCH` finishes it.

### rename codes

`rename` refuses before it changes anything, except `rename_failed` (undone) and `rename_incomplete` (finish it by running the same command). Reused codes: `unknown_workspace`, `checkout_missing`, `detached_head`, `rebase_in_progress`, `workspace_name_case_conflict`. `details.workspace` and `details.branch` are the current names; the new ones are `details.new`, or `new_workspace`, `new_branch` and `new_path` in `rename_target_taken`. `details.fix`, where listed, is a command that clears the refusal.

| Code | Meaning |
|---|---|

| `run_active` | A workflow run is still going on the checkout, a gate wait included. `details.run_id`, `details.path`. |
| `dev_lock_held` | The checkout holds the `devenv` lock. Run `workspace dev down` first. `details.path`, `details.workspace`, `details.fix` (`workspace dev down NAME`). |
| `rename_main_checkout` | The workspace is a main checkout. `details.workspace`, `details.path`. |
| `rename_not_worktree` | The workspace's name has no `.worktree-` part, or its checkout is not a linked worktree. `details.workspace`, `details.path`. |
| `rename_pull_request_branch` | The branch, or the new name, is a `pr-N` branch. `details.branch`, `details.new`. |
| `rename_no_change` | The branch already has that name. `details.branch`. |
| `rename_invalid_name` | The new name is not a branch name git accepts, leaves no directory name, or makes a config file name (`workspace.<name>.yml`) over 255 bytes. `details.new`; for the length `details.reason` (`too_long`), `details.bytes`, `details.limit`. |
| `rename_target_taken` | A new name is taken. `details.taken`: any of `branch`, `branch_conflict` (a branch that can't coexist with the new name as a git ref, `a` and `a/b`; `details.conflicting_branch`), `directory`, `config`, `state_key`, `state_dir`, `project_settings`, `socket`, `agent_log`, `inbox`, `hook_events`, `session` (the new tmux session name), `notes_target` (`details.notes_path`); `details.new_workspace`, `details.new_branch`, `details.new_path` (always the new checkout path), `details.paths` (the files in the way, by what is taken), `details.fix` (the `rm` command, when only `agent_log`, `socket` or `hook_events` are in the way). |
| `rename_case_only` | The new worktree directory differs from the old one only in case, which the file system may not move. `details.from`, `details.to`. |
| `rename_locked_worktree` | The worktree is locked (`git worktree lock`). `details.path`, `details.fix` (`git worktree unlock PATH`). |
| `rename_in_progress` | An earlier rename was started and not finished; run the same command again to finish it. `details.workspace`, `details.new_branch` (the name that rename was for), `details.rerun` (`true`), `details.fix` (the command). | `rename_failed` | A git step failed and was undone, or the rename could not begin. | `rename_incomplete` | The rename stopped after the git steps, or the undo of one failed. The journal is kept; the same command finishes it. `details.workspace`, `details.new_workspace`, `details.new_branch`, `details.failed` (the steps; `startup_lock` on a re-run that could not take it), `details.problems`, `details.rerun` (`true`, or `false` when no config is left under either name and a re-run can not finish), `details.fix` (the command, or the `rm` of the journal), `details.signal` when a signal stopped it. |

The plan (`rename --dry-run --json`, from `RenamePlan::Plan#to_h`) has these fields:

| Field | Meaning |
|---|---|
| `project` | The main project's name. |
| `workspace`, `branch`, `path`, `session` | Each an object `{from, to}`: the value now and after. `path.to` equals `path.from` when only the branch changes. |

| `resume` | `true` when the plan was made for a re-run that finishes a half-done rename. |

| Code | Meaning |
|---|---|
| `upstream_other_name` | The branch keeps tracking a remote branch under the old name; `push` will refuse (`push_rejected`, `details.reason` `upstream_mismatch`) until it is renamed or unset. `upstream`. |
